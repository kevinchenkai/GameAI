## 写工单的六条教训

> 前五条来自 [Juscent/lover 项目](/Users/kk/Work/chenkai_airepo/Juscent/lover/orders/README.md) 的实战踩坑，
> 第六条是本项目自己的。

### 1. 🔴 判据必须**物理可达**

不可达的判据会把执行者逼到「违反判据」和「凑数报 ✅」之间二选一 ——
**两个结果都比没有判据更糟**。

**本项目已经犯过两次**：

| # | 不可达的要求 | 为什么不可达 | 怎么改的 |
| --- | --- | --- | --- |
| 1 | 「美术在 PNG 里定义 tail 的旋转锚点」 | **PNG 格式存不了 pivot 数据** | 职责划分：美术定「哪里该转」，代码定「准确从哪个坐标转」 |
| 2 | 「输出 1024×1024 真透明 PNG」 | **内置 `image_gen` 只能出 1254² 无 Alpha** | 改为**后处理**保证尺寸与透明（[SPEC §6.5](./LEGIBILITY-SPEC.md)）|

> 🔴 **第 2 条的教训**：**工单不能把工具做不到的事写成硬性交付条件。**
> 第一轮 Codex 因此拒交（处理是对的），但**卡住的是工单，不是它**。
>
> 📌 **写工单前先问**：这条要求，**执行方手里的工具能做到吗？**
> 做不到就要么换工具，要么改成"生成 + 后处理"两步。

### 1.1 🔴 **改判据时要顺着链条查一遍**

修 #2 时我一开始给全部 20 段 prompt 统一加了
「若不支持 Alpha 就画白底，之后抠图」——
**但叠加层与冰块这 5 张本身就要求半透明**，
白底抠图**在物理上无法还原半透明**（分不出"该透明的背景"和"该半透明的主体"）。

**一个修复动作制造了一条新的不可达判据。** 已分成两类：

| 素材 | 方案 |
| --- | --- |
| 不透明素材（棋子 / 旺财 / UI / 院门，11 张）| ✅ 白底 + 抠图 |
| **半透明素材**（3 叠加层 + 2 冰块）| 🔴 **必须真 Alpha，做不到就停下报告** |

### 2. 🔴 判据之间**不能互相矛盾**

写完工单**自己先过一遍**：有没有哪两条要求指向相反的方向？

**本项目的一处潜在矛盾已提前处理**：
「棋子要有立体感」与「高光阴影各 ≤30% 面积」方向相反。
已明确取舍 —— **立体感是次要目标，明度可辨识优先**，并写进
[LEGIBILITY-SPEC §4](./LEGIBILITY-SPEC.md)。

### 3. 🔴 别要求「像素级一致」—— 那本来就做不到

独立生成的图不可能像素级一致。判据应该是「**在游戏里看不出破绽**」。

本项目对应的写法：Puppet 与整图状态要求「**构图位置一致，切换时不跳**」，
而不是「像素级对齐」。

### 4. 🔴🔴 判据写错时，**执行者会比判据更严格**

📌 **执行者报告的失败，要逐条复核，别照单全收** ——
它严格照判据执行，**判据错了它就会拒掉对的东西**。

### 5. 🔴 「一致性」判据必须**逐件写死**，写类别等于没写

| ❌ 写法 | ✅ 写法 |
| --- | --- |
| 「同一只小狗」 | 「奶油至浅棕毛色，**粗短上翘尾巴**，**无项圈**，头身比 2.2:1」 |
| 「统一风格」 | 「左上 45° 光照，哑光微光泽，**高光 ≤1/3 面积**，阴影非纯黑」 |

**本项目又栽了一次**：头身比原本只写「a stylized head-to-body ratio of roughly
2.2 to 1, so the head is noticeably large」——
`noticeably large` 太软，**三个候选全部画成接近 1:1 的写实比例**。

已改为**给出可执行的对照与判据**：

| ❌ 原写法 | ✅ 现写法 |
| --- | --- |
| `the head is noticeably large` | `the HEAD IS MORE THAN TWICE AS LARGE as the torso and is the single dominant shape` |
| （无反向约束）| `Do NOT draw realistic dog proportions where the head is roughly the same size as the body` |
| （无验收方法）| **缩到 128px 高仍能看清眼鼻嘴**，看不清就是头不够大 |

> 📌 **判断方法**：判据里有没有**只描述程度的形容词**
> （noticeably / slightly / clearly）？有 → 换成**可比对的量**或**可执行的测试**。

📌 **判断方法**：把判据念一遍，问「**两张都满足这句话，但看起来不一样，可能吗？**」
可能 → 判据不够具体。

📌 **另一条**：一致性判据要**指定一张基准图**（本项目指定
`pet-wangcai-master.png`），不要只写"互相一致" ——
**没有基准，N 张图有 N 种解释。**

### 6. 🔴 **本项目独有：算过的数值 ≠ 画出来没问题**

色板的灰度值是**纯色块**算的，但实际图有高光、阴影、纹理，
**会把有效明度往中间拉**。

量化后发现：**全部 5 对相邻色的高光/阴影区间都是重叠的**
（见 [LEGIBILITY-SPEC §4.1](./LEGIBILITY-SPEC.md)）。

**所以 40px 灰度联合测试是硬性的，不能因为"色值已经算过"就跳过。**

> 📌 **可迁移的教训**：
> 任何"我们已经在设计阶段算过了"的结论，
> 都要问一句「**实际产出会不会引入算式里没有的变量？**」
> 这里的变量就是高光、阴影和纹理。
