## 1. B1 叠加层重做：验收脚本比工单更重要

用户点名"火箭/炸弹很丑"。这一项**返工了两批**（第 5 批、第 6 批），
教训不在美术，在**我写的验收判据**。

### 1.1 第一版判据是错的 —— 均值差掩盖了一切

初版 `tools/check-overlays.py` 用**平均亮度差**衡量可见性，
结果报出紫色棋子 Δ=1.2（判定"完全看不见"），而把合成图渲染出来一看：
**金色箭头清清楚楚**。

原因：叠加层是"深色描边 + 亮色芯"，两者一平均正好等于紫色的均值。
**均值差衡量不了"局部有没有对比"。**

改成**芯部 P90/P10 对背景中位数**，且双向取大：

```python
def delta(comp, piece, m, ref_mask) -> float:
    lm = luma(comp[..., :3][m]); lp = luma(piece[..., :3][ref_mask])
    base = float(np.median(lp))
    bright = float(np.percentile(lm, 90)) - base
    dark = base - float(np.percentile(lm, 10))
    return max(bright, dark)     # 亮标记与暗标记都算数
```

> 📌 亮度一律用 **BT.709**（0.2126/0.7152/0.0722），全项目统一，勿混 BT.601。

### 1.2 差点把判据修得太严

修完之后我准备再加一条"必须同时满足色距 ≥ 90"。
**先拿已知合格的旧素材跑了一遍** —— 旧图在黄色棋子上色距只有 20.2，
但亮度差高达 132，肉眼极清楚。若加成 AND，会把明明合格的图判死。

最终规则是**「亮度或色距，二者不可皆失」**：

```python
wins = d >= STRONG_DELTA or dist >= MIN_CORE_DIST   # 60 / 90
ok   = d >= MIN_DELTA and wins                      # 20
```

> 🔴 **判据必须双向验证**：既要拿不合格样本确认它拦得住，
> 也要拿**已知合格样本**确认它不误杀。只验一个方向 = 编码了错误的规则。

### 1.3 第 5 批：数字全过，肉眼否决

第 5 批所有指标达标，但渲染出来一看：Codex 是靠**削掉亮芯**来压跨度的
（芯部 P95 从 221~241 掉到 135~137），而且炸弹配色撞上了橙色水果
（芯部色距 107 → 51）。**数值合格 ≠ 交付合格。**

于是给判据补两条**下限**（不只有上限）：

```python
MIN_CORE_LUM  = 190.0   # 芯部 P95 亮度下限：压跨度只能靠柔化过渡，不许降亮芯
MIN_CORE_DIST = 90.0    # 色距达标线
```

第 6 批（火箭改单向大箭头、炸弹保留球体与引线）一次通过，退出码 0。

### 1.4 上线后仍然"没变" —— 30 天图片缓存

用户反馈"火箭炸弹还是旧样式"。服务器上字节确实是新的，
但 nginx 对静态图 `expires 30d`，**同名文件在设备上 30 天内不会重新拉取**。

改名 `overlay-*-v2.png` 解决。根 CLAUDE.md 早就写了「改图请换文件名」，
这次是我没照做。

## 2. A1 消除粒子：三个只有浏览器能发现的问题

`fxPlan.ts`（纯函数、可单测）+ `MatchFx.ts`（Phaser 侧）+ `fxQuality.ts`（降级）。
粒子贴图是**代码生成的径向渐变点**，零美术素材。

**单测全绿，但浏览器里三处不对**：

| 症状 | 真因 |
| --- | --- |
| 粒子全是白的，六色分不出 | `blendMode: 'ADD'` 在米色底上把所有颜色都洗成白色 → 改 `'NORMAL'` |
| 粒子小到看不见 | `sizeRatio: 0.16` 在 84px 格子上只有 9.5px → 0.28，并把贴图芯部加宽 |
| 特殊棋子生成没有放大脉冲 | 该事件时间轴时长为 0，`finish()` → `settleTweens()` 在渲染任何一帧之前就把 tween 补完了 → 该 tween 故意**不注册**进 `pendingTweens` |

> 📌 再次印证记忆里那条：**渲染层改动，单测全绿不代表画得出来。**

`FxQualityMonitor` 还有个自己找出来的 bug：一段持续掉帧会连降两档
（high → medium → low）。加 `coolingDown` 标志，一段慢只降一档。

## 3. 音效：真因是**时序**，不是频率

用户逐项核对后给出关键数据：**#1 挥手/交换有声，#3 #4 #6 #7 没有**。

我第一次归因到"频率太低，小扬声器放不出"——这**是**一个真实问题
（`AUDIBLE_BAND` 下限 200Hz 是"理论可听"，不是"手机扬声器放得响"，实际地板约 300Hz），
但它解释不了为什么 #1 能听见。

真因：`consume()` 把 match 音排在 **60ms**，而画面动画在 **234ms** 才开始 ——
**音效比画面早 174ms**，正好撞在 swap 音上被节流吃掉。

修复是让音频消费**与画面同一条时间轴**：

```ts
const timeline  = buildTimeline(events, this.getTempo());
const atByIndex = timeline.items.map((i) => i.atMs);
for (const cue of planSfx(events, atByIndex)) { ... }
```

`planSfx` 因此改为接受动画时间轴。频率调整保留（它是次要但真实的问题）。

> 🔴 **教训**：我拿到"没声音"就先归因到自己最先想到的原因。
> 真正定位靠的是用户给的**对照数据**（#1 有声这一条）——
> 单一现象可以有多个解释，**能区分它们的是反例**。

### 3.1 顺带修掉一条空转的测试

我写过一条「紧跟 match 的 spawn 不被吃掉」，**把 bypass 删掉它照样过** ——
因为节流是**按音名**的，两者本来就不冲突。
改成「一回合两个特殊棋子都要响」，删掉 bypass 会红。

> **不会失败的测试不是测试。** 新增测试应当验证：改回旧代码它会红。

## 4. 电脑浏览器适配

用户："header、settings 很乱"。实测 1920×1080：棋子长到 **150pt**（手机上 49pt），
棋盘吃掉 1048px，HUD / 旺财 / 控件被挤成 **0 高度**。

原来的布局只有棋子**下限**，没有上限，也没有内容区限宽。补两条（`config/tuning.ts`）：

```ts
maxPieceSizePt: 64,       // 棋子上限
maxContentWidthPt: 480,   // 内容区限宽
```

`layout.ts` 里限宽后左右留白 `gutter`，**四个区块共用同一个左边界** ——
只居中棋盘会让 HUD 与它错位。

再加"可见边界 + 淡背景"（参考 soulmate 的做法，纯 CSS 渐变，零素材，写在 `index.html`）：

- 门槛用 **min-width + min-height + pointer:fine** 三条件 ——
  只判宽度的话，横过来的手机（896×414）会被当成电脑，套上边框后高度更不够
- `#game` 高度 `clamp(700px, 100dvh - 64px, 920px)`。
  **700 是实测临界值**：1280×700 窗口上旺财区被压到 74pt（< `petMinHeightPt` 96），
  与「设置」按钮**叠在一起**；逐档量下来 680px 仍不达标，700px 才够
- 用 **flex 居中**而非 `translate(-50%,-50%)`：框比窗口高时后者会把**顶部 HUD 切掉**

一条既有测试「棋盘必须铺满可用宽度」与限宽冲突（iPad mini 上红）。
**没有删它**，而是把它限定到窄屏并写清理由 —— 它守的仍然是真实约束。

## 6. 旺财尾巴（用户："往右偏一点"）

直觉是往右移，**但右边一格都没有**：尾图最右不透明像素在 x=223，
body 画布 512 宽 → `rig.x` 必须 < 289，现值 286 已经贴到上限。
（我第一次改成 306，立刻被既有测试「尾巴不能超出 body 画布」拦下。）

期间还修正了自己的测量脚本：它把 `rig.x` 当成**锚点**，
而 `PetView` 把它当作该层的**左上角**（`PetView.ts:79`）。

把四层真拼出来看，违和不在左右而在**高低**：尾根从**后背**冒出来，
与臀部之间有空档。`y` 134 → 164 后尾巴自然接在屁股上，"往右偏"的观感由此达成。
