## 2. 5 个验收问题 → 怎么观察

框架定的 5 个问题，加上**具体的观察点**与**已知风险**。

### ① 三消爽不爽？

**看**：连锁发生时用户有没有反应（笑、"哦"、身体前倾）。

**已知风险**：
- 特殊棋子的**清除范围是否可预测**。框架 §5 特别提醒过这条：
  各家三消惯例不一致，玩家真正需要的不是"符合行业惯例"，
  而是**能预测这个特殊棋子会清哪里**。
  → **专门观察理解率。若频繁误判，立即改成视觉最直觉的方案，不要坚持理论。**
- 叠加层美术已重做，但**"看得懂"与"好看"是两回事** ——
  重点仍是观察玩家能不能预判火箭清一行、炸弹清一片。

### ② 旺财烦不烦？

**看**：用户会不会主动提到它？是"这狗真可爱"还是"它一直在动有点吵"？

**已知风险**：
- Idle 微动作是**一直在动**的（摇尾 900ms 周期、呼吸 2600ms）。
  设计假设是"活泼"，但也可能是"晃眼"。
- Hint 在发呆 **5s**（`hintAfterMs`）后让目标棋子**轻微呼吸**，
  10s（`repeatAfterMs`）重复；3s（`thinkingAfterMs`）时旺财先进入 thinking。
  设计上刻意不弹窗、不画箭头（"提示，不催促"），
  但对 50+ 用户可能**太隐晦以至于没注意到**。
  → 观察：发呆超过 5 秒的用户，有没有真的顺着提示走？

### ③ 50+ 用户不解释会不会玩？

**🔴 这是最重要的一个问题。** 不要提前教学，把手机递过去看他自己怎么办。

**看**：
- 第一次交换是"拖"还是"点两下"？（两种都支持）
- 看不看得懂 HUD 的"剩余步数"和目标图标？
- 通关后知不知道要点"下一关"？
- **会不会自己找到花园？**

**已知风险**：
- **没有任何新手引导。** Stage 0 刻意没做，就是要测"不解释会不会玩"。
  > 📌 实测确认（2026-08-09）：L1 的关卡数据里**有** `tutorial` 字段
  > （"滑动相邻的两个水果…"），但**全项目没有任何地方渲染它** ——
  > 只有 `types.ts` 声明与 `validateLevel.ts` 校验。
  > 所以"零引导"是**事实**，不是错觉。若测下来确实需要引导，
  > 数据已经在了，**只差一个渲染**，成本比想象的小。
- 目标区用的是**棋子贴图**而不是文字（"收集 12 个黄色"要求玩家把
  "黄色"翻译成"香蕉"，直接画香蕉就不用翻译）—— 这个设计是否成立需要验证。

### ④ 棋子够不够大？

**已做的**：8×8 → **7×7**，棋子边长 +14.3%（iPhone SE 42.9 → 49.0pt），
棋盘占屏宽 91.5%。

**看**：会不会眯眼？会不会点错相邻格子？

**已知风险**：六色的**明度差**理论上达标（最小 22.7 ≥ 20），
但真实环境（昏暗、老花、屏幕色偏）是另一回事。
→ 观察有没有把**梨看成蓝莓**、**葡萄看成苹果**（这两对明度差最小）。
若出现，是重出棋子的信号。

### ⑤ 院门建设是否让玩家愿意继续下一关？

**这是留存的核心假设。** 结算页刻意显示"院门还差 N 颗星"，
就是要卡在"还要不要再玩一关"的决策点上。

**看**：
- 看到"还差 1 颗星"时，会不会**主动**点下一关？
- 建设完院门有没有情绪反应？
- 会不会为了修院门而多玩几关？

**已知风险**：3 关才建一阶段（`nodeStageCost: 3`），**可能太慢** ——
院门 3 阶段共需 **9 颗星**。若用户在第 5~6 关就流失，说明反馈周期太长。

## 3. 主持人速查卡（一页，照着做）

### 开始前 2 分钟

- [ ] 用**他自己的手机**打开 https://g.ismayday.mobi/garden/
- [ ] iPhone：**确认侧面静音开关拨到响铃档**（静音时整个网页都没声音，这不是 bug）
- [ ] 如果这台手机之前玩过：需要**清掉存档**才能测"第一次上手"
      → Safari：设置 → Safari → 高级 → 网站数据 → 搜 ismayday → 删除
      （嫌麻烦就换一台，或用无痕窗口）
- [ ] 准备好 §4 的记录表 + 笔；**手机计时器**开着

### 开场白（照念，不要多说）

> "这是个小游戏，你玩玩看。**我不教你**，你想怎么点都行。
> 玩的时候**想到什么就说出来**，觉得奇怪也说。没有对错，是我们在测这个游戏。"

**然后闭嘴。**

### 过程中的三条纪律

| 🔴 不要 | ✅ 要 |
| --- | --- |
| 不要解释怎么玩 | 记下他**卡了多久**、**试了什么** |
| 不要在他卡住时提示 | 卡住 **≥60 秒**才介入，并**记下"此处需要引导"** |
| 不要替他点屏幕 | 记下他**说的原话**（原话比你的总结值钱） |

**唯一可以说的话**：他问"这样对吗？"→ 答"你觉得呢，你试试。"

### 计时锚点（写在记录表上）

| 记什么 | 为什么 |
| --- | --- |
| 第一次**成功**交换的时刻 | 测"不解释会不会玩"的硬指标 |
| 第一次通关的时刻 | |
| 每一次**卡住 ≥15 秒**的位置 | 卡点就是设计缺陷所在 |
| 结束时**玩到第几关** | 判断难度曲线与流失点 |

### 玩完之后再问（不要提前问）

1. "刚才哪里让你觉得**别扭**？"
2. "**那只狗**你注意到了吗？"（不要问"喜不喜欢"——会得到客套话）
3. "**看得清**吗？"（递回手机，让他指哪个看不清）
4. "还想再玩吗？"→ **观察他有没有真的又拿起手机**（行为 > 回答）

## 5. 测试方法

| 项 | 建议 |
| --- | --- |
| 人数 | 50+ 与 8~15 岁各 2~3 人 |
| 时长 | 每人 **20~30 分钟**，不打断（至少要能玩到 L3~L4 才看得出难度曲线） |
| 设备 | **用他们自己的手机**（我们的测试机不代表真实环境） |
| 引导 | **零引导**。只说"你玩玩看" |
| 记录 | 用 §4 的表；卡点、原话、皱眉的瞬间 |

⚠️ **不要在旁边解释**。用户一旦被教会，问题 ③ 就再也测不出来了。
想问的话等他玩完再问。

⚠️ **一个人测完再测下一个**，不要两人同时玩 —— 会互相提示。

⚠️ **不要录像后再看**。卡住的那几秒，人的表情和手上的犹豫是当场才有的；
录像里只看得到"他点了哪里"。

## 7. 测试前必须实机确认的一项

**iPhone 微信内的音效。**

已改了三处（每次手势重试 `resume`、播静音 buffer、await `resume()`），
浏览器里验证过 suspended → running 的自救路径，
**但没有在真实的 iPhone 微信里验证过**。

→ 开测前请用 iPhone 微信打开一次，确认有声音。
若没有，**先确认侧面静音开关**（那不是 bug）。

## 8. 测完之后

按反馈优先级，手上已经排好的候选改动：

| 若反馈是… | 对应改动 | 成本 |
| --- | --- | --- |
| "建设太慢了" | 调 `GARDEN_ECONOMY.nodeStageCost`（现为 3） | **极小**（一个数字） |
| "第 6 关老是过不去" | 调 `stage0.ts` 里该关的 `moves` / 目标 `count` | **极小**（改数据不改代码） |
| "棋盘老是自己动" | 已从源头解决；若仍出现，查 `REFILL_MAX_ATTEMPTS` | 小 |
| "不知道该干什么" | **渲染 L1 已有的 `tutorial` 字段**（数据已在，只差 UI） | 小~中 |
| "看不出这是什么" | 从 `candidates/` 直接切候选图；不行才重出 | 小~中 |
| "旺财不够生动" | thinking / hint 专属动作（**已挂着**） | 中 |
| "太素了" | B2 背景图（**已决定暂不做**，有反馈才做） | 中（需 Codex） |

> `candidates/` 里还留着每张素材的 2~3 个落选版本（110 MB）。
> 若测试反馈要换某张棋子，**可以直接切，不用等 Codex 重出**。
> 这也是为什么它留到 M8 之后再清理。

### 整理反馈的原则

1. **行为 > 说法。** "我觉得挺好的"配上"他再也没拿起手机"——以后者为准。
2. **卡点先于喜好。** 三个人卡在同一处 = 必改；三个人对配色看法不同 = 先不动。
3. **别急着改。** 测完 4~6 人再一起排优先级；改一个就再测一轮会浪费被试。
