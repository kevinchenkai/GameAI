## 1. 最贵的三个教训

这三条是本阶段**反复**出现的模式，值得单独拎出来。

### 1.1 🔴 单测全绿 ≠ 渲染层没问题

**出现次数：4 次以上。**

| 事故 | 单测状态 | 真实表现 |
| --- | --- | --- |
| 特殊棋子消除后精灵不销毁 | 467 条全绿 | 用户截图：一格里两个棋子重叠 |
| 7×7 改了关卡数据但渲染没跟 | 473 条全绿 | 棋盘还是 8 列格子，棋子没变大 |
| 旺财 `hint` 状态被自己覆盖 | 535 条全绿 | 状态机永远进不了 hint |
| 花园页按钮压住进度文字 | 578 条全绿 | 文字被盖住一半 |

**共同点**：数据是对的，**接缝**是错的。单测各测各的模块，没人测"A 的输出真的进了 B"。

**对策**（已固化）：
- 渲染层改动**必须在浏览器里实跑**，并且**读运行时状态**而不是只看截图
  （旺财那次截图完全正常，是查 `pet.getState()` 才发现的）
- 浏览器 pane 会节流 rAF，要用 `g.loop.step(performance.now()+i*16)` 手动驱动
- 开发期 `window.__GAME__` 句柄（`import.meta.env.DEV` 守卫，生产被 tree-shake）

### 1.2 🔴 "算过" ≠ "画出来没问题"

美术工单 §5 早就写了这句警告，本阶段两次验证了它：

1. **棋子明度**：配置里的规格值自洽（最小差 25.7），但测试查的是**规格**不是**真实 PNG**。
   补上读像素的测试后确认交付图达标（最小 22.7），**但这是运气好**——
   测试原本抓不到任何偏差。
2. **叠加层可见性**：我给 Codex 的工单判据写错了（把冰的遮挡约束套到标记层），
   Codex 每个数字都达标，结果在浅色棋子上**完全看不见**。已记入 LEGIBILITY-SPEC §5.2。

**对策**：凡是"这张图能不能看清"的判据，测试必须**读真实 PNG 的像素**。

### 1.3 🔴 度量口径必须和规格用同一个

我用 BT.601 量棋子明度，算出 green/blue = 17.0 低于判据，**据此写了一份重出工单**。
换回项目在用的 BT.709 后是 25.2，全部达标 —— 工单作废删除。

两个公式对绿通道权重差很多（0.587 vs 0.7152），而绿蓝紫的判定最依赖绿通道。

**对策**：写验证脚本前，先确认规格用的是哪个公式。已把这条写进 `palette.test.ts` 注释。

## 2. 按里程碑记录

### M0~M1 · 骨架与核心引擎

**关键决策：`core/` 零引擎依赖。**

`core/` 与 `config/` 禁止 `import Phaser`（eslint 强制）。收益不是"架构好看"，而是：
- 关卡可解性能用脚本跑 200 局模拟（`npm run simulate`）
- 连锁与特殊棋子的组合能在 Node 里 fuzz（40 个种子 × 30 步）
- 渲染层可替换

**踩的坑**：`createSession` 漏了"把关卡配置里的障碍放到棋盘上"这一步。
后果是**破障目标永远无法完成** —— 配置里写了冰，盘上一块都没有。
类型检查全过，测试也全过（因为测试用的是手工构造的棋盘）。

### M2~M4 · 素材接入与渲染

**首次部署全部素材 404。** 原因：`config/assets.ts` 里的路径写成硬编码 `/assets/...`，
JS/CSS 由 Vite 自动加了 `base` 前缀（`/garden/`），但**手写字面量 Vite 不处理**。
本地开发正常（开发期 base 恰好是 `/`），线上全白。
→ 改用 `import.meta.env.BASE_URL`，并加测试守住（`assets.test.ts`）。

**Phaser Loader 的坑**：素材 404 时**不会中止**，照常走完 `complete`，
然后场景拿着一堆空纹理去画 —— 表现是"游戏起来了但什么都看不见"，控制台只有一行 warn。
→ 必须监听 `FILE_LOAD_ERROR`。

### M5 · HUD、音频、结算

**音频用合成音，零素材依赖**（`assets/audio/` 至今是空的）。
WebAudio 直接合成，将来有真素材换掉 `WebAudioManager` 即可，接口不变。

**50+ 听力约束**：音效基频限制在 500Hz~2kHz。
我用 `OfflineAudioContext` + DFT 实测频谱，发现 `sawtooth` 波形把
`specialFire` 47% 的能量放到了 2kHz 以上 —— **基频合规不等于能量合规**。
→ 波形限制为 sine / triangle。

**文案纪律**（都写进了 `config/pet.ts`）：
- 失败页标题是「就差一点点」，不是「关卡失败」
- 按钮是「再试一次」，不是「重新开始」
- 输了**不显示 0 星** —— 那等于把"你一颗都没拿到"再说一遍
- 设置项叫「节奏」不叫「难度」，选项是「舒缓/明快」不是「慢/快」
  （"简单模式"对 50+ 用户是羞辱，他们宁可玩得难受也不会去开）

### M5.5 · 用户实测反馈的四件事

用户在真机上提了四条，全部处理：

**① 字体模糊** —— Phaser 默认把 canvas 缓冲设成 CSS 尺寸，
手机 DPR=2/3 等于把画面**拉伸 2~3 倍**。棋子是圆润插画看不太出，
**文字笔画边缘高对比，一拉伸立刻发虚**。

修法：`Scale.NONE` + `resize(css*scale)` + `zoom: 1/scale`，倍率封顶 2
（3x 屏是 9 倍填充率，老机器会掉帧）。

⚠️ 连带影响很大：游戏内坐标从此是**物理像素**，所有字号/间距/圆角/SafeArea 都要换算。
我中途只改字号没改布局常量，**设置面板整个叠成一团**。
→ 加了 `game/ui/uiScale.ts` 集中换算，禁止各处手写 `* scale`（漏乘不报错，只会小一半）。

**② 棋盘 7×7** —— 见 §3.1，这条单独讲。

**③ iPhone 微信无音效** —— 三处缺一不可：
- 每次手势都重试 `resume()`（iOS 会反复挂起 context，不只第一次）
- 播一段**静音 buffer**（iOS 认可"用户允许放声"的标志动作，只 resume 不发声部分 WKWebView 仍静默）
- `resume()` 要 **await**（它是 Promise，`void` 掉的话音符排到 suspended 的 context 上，永远不响且不报错）

⚠️ 有一条**代码解决不了**：iOS WebAudio 受**手机侧面物理静音开关**控制。

**④ 叠加层美术难看** —— 用户明确说"记下，最后再优化"。**未做，仍挂着。**

### M6 · 旺财

**Puppet 5 层合成**（tail/body/ears/eyes），不用整图。
Idle 微动作是主体：摇尾、呼吸、随机眨眼、耳朵抖、偶尔抬头看玩家。

> 核心洞察（写在 `config/pet.ts`）：玩家感知到的"这只狗很活泼"，
> **80% 来自它在你不操作时也一直在动**，而不是庆祝得多用力。
> 前者零预算成本，后者是稀缺资源（重反应预算只有 8%）。

**Rig 校准踩的两个坑**：

1. **`preview-composite.png` 不能用来反推坐标。**
   它看着就是那 5 层叠出来的，我拿它做穷举对齐 —— 尾巴在全图找不到任何匹配位置
   （最优色差 254/765）。查下去发现它是**整体重绘**的效果图：
   在 body 不透明区内，与 `body.png` 的像素一致率只有 **77.2%**。
   → 它只能当风格参考。坐标改为按各层几何 + body 解剖参考点算，**然后拼出来核对**。

2. **算出来对、拼出来错。**
   我按"耳朵根部要埋进头里"算出 `ears.y = 18`，数学上讲得通。
   拼出来一看耳朵陷在额头上像两条眉毛 —— 正确值是 **`-36`**（负数才对，
   因为 ears 画布上方本来就有 72px 空白）。

3. **尾巴悬空**（用户问"尾巴有没有贴在屁股上"才发现）。
   我当时检查过接合点：根部中心落在 body 内、alpha=254，数值上"贴住了"。
   但把臀部**放大 3 倍**看，根部下缘和臀部之间有一条明显白缝。
   → 判据错了：不能看"根部中心在不在身体里"（一个点当然容易落在里面），
   必须是"**根部断面的每一个像素**都在身体里"。已写成测试。

**契约落地**：`PetController` 不碰 Phaser，表现委托 `PetPresenter` 接口 ——
规则（优先级、一段连锁最多一次重反应、超预算降级）因此能在 Node 里单测。

### M7 · 花园与存档

**两条最容易写错的规则**（框架 §8.2 点名"实现时容易漏"）：

```ts
// ① Progress Star 只在首次通关发放
const firstClear = prev === 0 && rating > 0;
// ② Mastery 按历史最高的增量，夹 0（不能倒扣）
const masteryGained = Math.max(0, rating - prev);
```

写成"每次通关都 +1"不会有任何报错，但玩家**重打第 1 关十次就能把院门修满** ——
而 Stage 0 要验证的恰恰是「再玩两关就能修好院门」这个心理，
一旦被绕过，**整场真人测试的结论都不可信**。

**结算页必须显示花园进度**（框架 §8.1 明确要求）。
不是为了信息完整，是为了卡在"还要不要再玩一关"的决策点上 ——
只在花园页显示就晚了，那时玩家已经决定退出。

进度用**离散格子**不用连续进度条：规则是"3 颗星建一阶段"，
连续条会让人以为差一点点就能建，实际还差一整颗。**离散格子和规则同构。**

## 3. 几个值得单独说的技术决策

### 3.1 7×7 的两次改动

用户说"8×8 对老人小孩可能太小，能否 7×7"。这件事做了**两遍**：

**第一遍（失败）**：我把 8 关全部改成 `cols: 7` 并重新调参，但**渲染层根本没读这个字段**。
`computeLayout()` 自己从 `[8, 7]` 里挑列数，判据只有"棋子 ≥ 38pt" ——
真机上 8 列永远达标，降级分支**从来没触发过**。
结果：关卡逻辑跑 7×7、棋盘却按 8 列格子铺，渲染成「**7 列 8 号格子**」，
右边空一条、棋子一点没大。**473 条单测全绿**，因为没有任何断言把
"关卡列数"和"实际渲染列数"连起来。

**第二遍（正确）**：列数属于关卡数据，不该由布局算法猜。
`LevelScene` 把 `session.board.cols` 传进 `computeLayout`，棋盘按这个列数**铺满可用宽度**。

实测棋子边长：iPhone SE 42.9 → **49.0**（+14.3%），棋盘占屏宽 79.7% → **91.5%**。

**副作用：难度全部要重调。** 7×7 少了 23% 的格子，8 关重新模拟：
其中一条只有模拟器能发现 —— **冰要往里放**。8×8 时代贴边的冰还够得到，
缩到 7×7 后同样位置把 L8 通过率拖到 **45%**。

### 3.2 首屏 4276 KB → 206 KB

分三步做的，**最大的一块不是压缩**：

| 步骤 | 省下 | 说明 |
| --- | ---: | --- |
| 院门移出 BootScene | 3064 KB | 花园页才用，关卡页根本不显示 |
| **删掉从没画过的贴图** | **660 KB** | 见下 |
| pngquant 压缩 | −63% | 20 张实际加载的素材 |

**「从没画过」是最意外的一条**：`uiPanelBg / uiBtnPrimary / uiBtnPause /
uiMovesBadge / uiObjectiveSlot / levelBg` 六张，渲染层引用次数**都是 0**。
Panel / HudView / ResultPanel 全部用 Graphics 画圆角矩形（这是刻意的：
要按 DPR 缩放、跟随主题色），从没用过整图。

这类浪费**没有任何症状**：不报错、不白屏、功能完全正常，只是所有人首屏多等一截。
→ 加了测试：BootScene 里 load 的每个 TEX 必须在渲染层被引用。

**压缩前先验了不破坏可读性判据**（本项目有 ≥20 灰度差硬约束）：
六色平均灰度漂移最大 **0.04**，2× 放大 A/B 目视无带状。

### 3.3 输入闸门（冻结契约 7）

`settled` **不解锁输入**。这是复查阶段修正的一条，理由：
`settled → levelWin` 之间存在竞态窗口，玩家可能在进入 Victory Flow 前抢下一步。

输入由 `TurnController` 状态机门控：
```
READY_FOR_INPUT → RESOLVING → BOARD_SETTLED → TURN_RESOLVED → PRESENTATION → READY_FOR_INPUT
```

⚠️ 实测踩到：过关后点「下一关」，新关卡相位仍停在 `PRESENTATION` ——
**输入永久锁死，棋盘看着正常但完全点不动，且无任何报错**。
原因：`scene.restart()` **不重建实例**，只再跑一次 `create()`，
所以字段初始化式（`private turn = createTurnState()`）只在第一次执行。
→ 所有跨局状态必须在 `create()` 里**显式复位**。

## 4. 当前遗留（按优先级）

### 🔴 M8 之前必须决定

**6 色关（L6~L8）死局率约 8%。**
实测降到 5 色可回落到 0.3%。这是「49 格 ÷ 6 色 ≈ 每色 8 个」的固有属性，不是 bug。
死局会自动重排、不扣步，但**看得见**。

当前模拟数据（200 局/关）：

| 关卡 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 通过率 | 100% | 100% | 100% | 95.5% | 97.5% | 77% | 80.5% | 87.5% |
| 死局率 | 0% | 0% | 0.5% | 0.5% | 1% | **8.5%** | **6.5%** | **8%** |

→ **待用户决定**是否降色。我倾向降（低压力定位下，"棋盘老是自己动"比"少一种颜色"更伤体验），
但这改的是难度曲线。

### 🟡 用户明确说"放到后面"

   逻辑正确，但视觉上只有 Idle 和跳跃两种表现；歪头、跑向提示方向没做。
3. **candidates/ 清理**（110 MB，179 个文件）
   已 gitignore、服务器上 0 个、代码零引用。
   **留到 M8 之后**：万一测试反馈要换某张棋子，手上有候选能直接切。
   ⚠️ 删掉会同时失去 AI 出图的原尺寸图（将来要 2x 高清版需重出）。

### 🟢 已知但不阻塞

- **Mastery Star 未启用**（Stage 0 不用，但发放逻辑已写对并测过，V1 Full 直接用）
- **进度码导出/导入未实现**（明确划到 V1 Full，调用会抛错）

## 5. 给接手者的提醒

**开工前必读**：[../CLAUDE.md](../CLAUDE.md) 的红线与 §3 冻结契约。

几条最容易违反的：

| 红线 | 为什么 |
| --- | --- |
| `core/` 不 import Phaser、不出现宠物概念 | 关卡模拟器与 fuzz 测试的前提 |
| 不用 `settled` 解锁输入 | 竞态窗口，见 §3.3 |
| 数值/台词/时长不写死进逻辑 | 策划改案应当只改数据 |
| 随机走 `core/rng.ts`，禁 `Math.random()` | 复现 bug 依赖它 |
| 部署不碰站点根 | 同服务器还有 mimo / mystock 等非本仓库项目 |

**验证流程**（缺一不可）：
```bash
npm test                              # 582 条
npm run build                         # tsc + vite
npm run simulate -- --all --runs 200  # 关卡可解性
```
渲染层改动**再加一条**：浏览器实跑 + 读运行时状态（见 §1.1）。
