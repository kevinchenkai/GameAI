## 1. 协作方法论：本项目最值得复用的部分 `[Claude]`

这套方法是项目能在 3 天内从零到上线、且质量可控的原因。

### 1.1 核心原则：**不采信报告，全部自己重跑**

Codex 每轮交付都附带「lint / test / build 全过」的结论。
Claude 的验收**从不引用这些结论**，而是：

1. 自己重跑 `npm run lint` / `npx vitest run` / `npm run build`
2. 自己重算对方报告里的每一个关键数字
3. 写**独立的对抗测试**（自己的 RNG、自己的 Solver、自己的取样脚本）

这不是不信任，而是**两个独立实现互相校验**才有意义。
实践中它抓出过真问题（见 §5）。

### 1.2 量化门槛：验收标准必须可判定

每轮改动前先定**数字门槛**，而非「看起来更好」：

```
❌ 「图案要更大一些」
✅ 「图案主体占卡牌 62%~68%，且不越 tile_frame 的 206px 安全区」
```

门槛写进文档 → Codex 实现 → Claude 逐条核对。
争议自然消解，因为双方对着同一个数字。

### 1.3 反向验证：**确认测试真的会红**

这是本项目最有价值的一条纪律。

新增防回归测试后，**故意把代码改回错误版本**，确认测试变红，再还原。
没做这一步的测试可能是「测了空气」——本项目实际发生过：

> M2 时我写的 Solver 剪枝交叉验证，复制了**错误的**剪枝逻辑，
> 结果在随机盘面上 0 个 mismatch——**这个测试根本没有鉴别力**。
> 后来改用 Python 穷举找到 3 个真实反例才证明问题。

### 1.4 分轮交付：结构与视觉分开

R2 拆成 R2-0（结构）+ R2-A（材质）分两次验收，**不合并**。
理由：结构改动的风险在布局与命中区，视觉改动的风险在参数数量，
混在一起出问题时无法定位。

### 1.5 争议处理：数据说话，谁对听谁的

本项目发生过 **3 次实质性技术争议**，全部以实测数据收场（§5）。
其中 **2 次是 Claude 错、Codex 对**。记录在案不是为了归咎，
而是这几次都改进了最终方案。

## 3. 设计阶段 `[Claude]`

### 3.1 从 V0.1 到 V0.3.4

初版 V0.1 由 GPT-5.6 生成，经四轮修订定稿。Claude 在设计阶段的主要贡献：

**发现并修正 §9.2 的数学错误（V0.2）**

我最初断言「4 种类型 + 7 格暂存槽 = 不可能失败」。**这是错的**：
`4 × 2 = 8 > 7`，四种类型每种放 2 张就已经溢出。
正确结论是**只有 3 种类型才绝对安全**（`3 × 2 = 6 < 7`）。

这个修正改进了设计——L1/L2 因此确定用 3 种类型，
新手前两关**数学上不可能失败**，符合休闲定位。

**难度阈值的三次教训**

V0.3.3 和 V0.3.4 两次把难度门槛定得比测量噪声还窄，导致
构建在未见过的随机种子上随机失败（「从 0.211 降到 0.205」= 0.6pp = 纯噪声）。

最终方案：

```
A. L1~L5 greedy ≤5%；L6~L20 ≤35%     （唯一硬性失败条件）
B. rate[i+1] >= rate[i] - 5pp         （容差 > ±4pp 的差值噪声）
C. avg(L6~10) < avg(L11~15) < avg(L16~20)   （分段均值）
— 删除「目标 ±3pp」硬门槛
```

**教训（后来又犯了两次，见 §5.2）**：
**定阈值前必须先算出该阈值在目标方案下的实际取值。**

### 3.2 冻结的接口契约

设计阶段定死、全程未违反：

1. `core/` 与 `config/` **零 Phaser 依赖**
2. `core/rules/` 是 GameModel / Solver / Simulator 的**规则单一真源**
3. 随机统一走 `SeededRandom`，**禁止 `Math.random()`**
4. `strict: true`，**不写 `any`**
5. 关卡数据必须过 Schema 校验
6. 素材路径**只走 Asset Manifest**

**上线时四条红线全部零违反**（§7 复查确认）。

## 4. Claude 的关键技术贡献 `[Claude]`

### 4.1 手机端 DPR 模糊修复（唯一由 Claude 实现的代码）

**用户反馈**：「字体很模糊，图片也不清晰」

**根因**：Phaser 的 `Scale.RESIZE` 把 canvas 像素缓冲设成 **CSS 尺寸**，
iPhone DPR=3 时等于让浏览器把整个画面**拉伸 3 倍**。

**为什么是「文字比图片更明显」**：卡片是圆润插画、色块平缓，糊一点不易察觉；
**文字笔画是高对比边缘，一拉伸立刻发虚**。用户的描述顺序精准指向了根因。

**这是第二次踩同一个坑**——garden 项目上线后收到过一模一样的反馈，
其 `main.ts` 至今留着注释「用户实测反馈的『字体很模糊』就是这个」。
StackPop 从零搭建时没沿用该方案，于是重蹈覆辙。

**修复**：`Scale.NONE` + `zoom: 1/scale` + 物理像素缓冲，**倍率封顶 2x**
（3x 屏是 9 倍填充率，老机器掉帧）。新增 `uiScale.ts` 换算层，
布局**先按 CSS 求解再整体放大**（直接喂物理像素会撞上 `tileSizeMax` 上限）。

**验证**：`buffer 750×1624 / CSS 375×812 = ratio 2.000`，
6 列 ground truth `52.17 / 44.34` **逐位未变**，11 项布局单测一行未改即全过。

**已固化**：写入长期记忆；`eslint-rules/requireScaledFontSize.js` 强制
场景字号必须走 `fontPx()` / `px()`（Codex 补充实现）。

### 4.2 UI 问题的量化诊断

三轮 UI 精修的**问题定位**均由 Claude 完成，且都是**先测量后判断**：

| 轮次 | 诊断 | 关键数据 |
|---|---|---|
| R1 | 图案被代码二次缩小 | 素材 68% × 渲染 0.70 = **实际只占 47.6%**，低于策划要求的 62~72% |
| R2-0 | 空白是结构问题不是氛围问题 | 残局最大单块空白 **占屏 54%**，没有背景美术能解决半屏空白 |
| R3 | 弹窗系统未跟上棋盘 | R2-A 只更新了 `drawToolButton`，弹窗用的是另外两个方法 |

其中 R2-0 那次，Codex 原方案把空白归为「氛围 / MA4 可选」，
Claude 通过模拟一局从开局到残局的空白变化（22% → 54%）证明它是**结构问题**，
并改判到材质精修**之前**执行——因为 HUD 与 Tray 的材质参数依赖周围留白，
顺序反了要重调一遍。

### 4.3 独立验收探针

除逐条核对门槛外，Claude 另写了独立探针，全部通过：

- **20 关初始盘面全部可解**（Solver 穷举，200k 节点预算）
- **打乱后仍可解**（抽样）
- **撤回栈有上限**（300 步长对局后 ≤120）
- **美术资源逐张验证**：解析 WebP 头比对尺寸/Alpha、测量图案 bbox 占比、
  检测抠图残留与边缘 fringing、计算两两亮度差与色相差

### 4.4 发布与部署纪律

- 每次部署**先 `--dry-run` 确认影响范围**，再实跑
- 部署后核对**本地与线上 md5 逐字节一致**
- 修改共享 nginx 配置时：先备份 → 确认规则唯一 → `nginx -t` 通过才
  `reload`（graceful）→ **逐个验证 9 个站点均 200**（含不归本仓库管的 mimo / mystock）
- 打 tag 前三项前置检查：工作区干净、测试构建全绿、两端 0 落后
- Tag 说明必须写清「**做完了什么、明确没做什么、怎么回滚**」——
  回滚点的价值在于半年后还知道它是什么

## 5. 三次技术争议与结论 `[Claude]`

**这一节是本文档最有价值的部分。** 三次争议全部以实测数据收场，
其中两次 Claude 错。

### 5.1 Solver 剪枝：Codex 对 ✅

**争议**：Claude 在 V0.2 §12.4 指定按**列顶牌类型**去重剪枝。
Codex 指出应按**整列内容**去重。

**结论**：Claude 用 ~4000 个盘面的 Python 穷举交叉验证——
按顶牌去重产生 **5 个假阴性**（把可解盘面判为不可解），按整列内容 **0 个**。
**Codex 是对的**，实现按整列内容：

```ts
const signature = column.join(',');   // 不是 column[column.length - 1]
```

**附带发现**：Claude 最初写的交叉验证测试**复制了错误的剪枝逻辑**，
在随机盘面上 0 mismatch——**这个测试没有鉴别力**。
这直接催生了 §1.3 的「反向验证」纪律。

### 5.2 R2-0 门槛：Codex 对 ✅

**争议**：Claude 定「深度 2 时空白 ≤25%、深度 8→2 差值 ≤10%」。
Codex 复算指出严格居中下两条**无法同时成立**。

**结论**：Claude 复核确认——实测深度 2 是 **27.15%**、差值 **16.29%**，
两条都不达标。**Codex 完全正确。**

**Claude 的错误**：这两个数是**按感觉定的，没有先算一遍能否成立**——
与 §3.1 的难度阈值是同一类错误，**第三次**。

**但 Codex 的替代提法也需修正**：它建议改成「上下空白差 ≤1px」，
但这测的是「是否居中」而非「空白是否可接受」，实测恒为 `0.00`，
**永远不会红，等于没有门槛**。

最终方案分成三条：最大单块空白 ≤28%（深度 1 放宽到 30%）、
上下差 ≤1px、**且相对旧算法必须减半**（实测各深度恰好 −50%，这才是真正的收益指标）。

> 后续 Claude 又发现自己连「≤28%」也没算全——深度 1 是 29.87%，
> **同一轮里犯了第二次**。已修正为分档门槛。

### 5.3 失败弹窗「打乱」是否为 bug：Codex 对 ✅

**争议**：Claude 在 R3 建议中把 `GameScene.ts:771` 的
`'打乱', false` 判定为「硬编码禁用的 bug」，因为弹窗文案写着
「撤回一步，**或重新整理牌面**」，却点不动。

**Codex 反驳**：失败态 tray 已满 7 格，而打乱**只重排 columns、不动 tray**，
启用后依然无法取牌。

**结论**：Claude 构造真实的 `tray = 7/7` 失败态实测：

```
findSolvableShuffle(...) → 抛 SafeStateUnavailable
  'Current tray cannot be rescued by any next pick'
```

**打乱在该局面下连一个合法结果都产生不了。**
按 Claude 的建议改，会做出一个「可点击但必然失败」的伪功能——比禁用更糟。
**Codex 是对的。**

**Claude 的错误**：只读了按钮那一行代码，**没回到 `core/` 验证启用后
功能是否真的成立**。

**但问题的实质确实存在**——文案在引导一个做不到的操作。
Codex 的修法与 Claude 相反且更正确：失败页只保留**真实可执行**的
「撤回 / 重来」，并新增 `shuffle.test.ts:70` 锁死该不变量
（Claude 反向验证过：去掉 throw 该测试立刻变红）。

**固化的纪律**：
> 提「某处禁用是 bug」之前，先验证启用后功能是否真的成立。
> 只看 UI 层的 `enabled` 参数不够，要回到 `core/` 跑一遍。

## 6. 美术流程 `[Claude 验收部分]`

美术由 Codex 用 Image Gen 分四批产出，Claude 逐批量化验收。

### 6.1 批次纪律

`MA0 Master Reference（定风格）→ MA1 前 4 个 Tile → MA2 后 4 个 + 背景 → MA3 UI + FX`

**不跳批**。MA0 的作用是把风格定死——若 MA1 发现风格不对，
只需重画 4 张而不是 23 张。实践中该纪律严格执行，未出现返工。

### 6.2 Claude 的量化验收

| 批次 | 关键发现 |
|---|---|
| MA0 | 图案占框 **~85%**，超出工单要求的 68% → **要求 MA1 改回 68%**（后来证明这个要求是对的，见下） |
| MA1 | 67.97% 达标；棋盘格抠图**残留仅 1px**，边缘是暖棕描边色而非灰边 |
| MA2 | 三条亮度约束全达标；另发现**最小亮度差不在 Codex 汇报的对上**——是 `paw`/`fish`（ΔL=2.4），靠宽高比 1.04 vs 1.93 分离 |
| MA3 | `tile_frame` 安全区实测 **206px**，容得下 174px 图案 |

**MA0 那条 68% 要求后来成了关键**：R1 修复「图案被二次缩小」时，
正因为素材是按 68% 做的，才能直接把渲染倍率改成 `1.00` 得到规格占比，
**不必重画任何素材**。

### 6.3 意外收获：色盲可玩

MA2 验收时 Claude 做了**灰度 32px 测试**——完全去色后，
八类图案仅凭剪影仍可区分。这意味着色盲玩家可正常游玩。

该特性已写入工程红线，后续调色不得破坏。

## 10. 经验总结 `[Claude 起草，Codex 补充]`

### 10.1 有效的做法 `[Claude]`

1. **不采信报告，全部自己重跑** —— 两个独立实现互相校验
2. **量化门槛** —— 把「更好看」翻译成可判定的数字
3. **反向验证** —— 确认测试真的会红，否则可能测的是空气
4. **分轮交付** —— 结构与视觉分开，出问题能定位
5. **争议以数据收场** —— 三次争议全部实测解决，两次证明 Claude 错
6. **批次纪律** —— 美术先定风格再铺量，避免大规模返工

### 10.2 踩过的坑 `[Claude]`

1. **同一个坑栽两次** —— garden 已解决过 DPR 模糊，StackPop 重蹈覆辙。
   **跨项目经验必须固化成可检索的记录**，否则等于没有。
2. **桌面验收挡不住移动端问题** —— DPR bug 在 DPR=1 上根本不存在，
   94 项单测全绿、构建通过、线上 200 全部无效。
   **移动端问题必须有可量化的检查**，而非肉眼看截图。
3. **定阈值前不先算** —— 犯了**三次**（难度阈值两次、R2-0 门槛一次，
   且 R2-0 那次同一轮里又漏算了深度 1）。
4. **换算层漏乘不报错** —— `px()` 漏一处不会崩，只是元素小一半。
   已用 ESLint 规则固化。
5. **只看 UI 层判断功能是否可用** —— §5.3 的教训。

### 10.3 对后续项目的建议 `[Codex 待补 + Claude 补充]`

**Claude 部分**：
- 新起 Phaser 项目**直接照抄 DPR 方案**，不要等用户反馈
- 从第一天就建立「量化门槛 + 反向验证」的验收闭环，
  成本远低于后期返工
- **跨项目的踩坑记录必须可检索**——本项目两次栽在同一个坑上，
  代价是一次线上事故
