## 1. 协作方法论：本项目最值得复用的部分 `[Claude]`

这套方法是项目能在 3 天内从零到上线、且质量可控的原因。

### 1.1 核心原则：**不采信报告，全部自己重跑**

Codex 每轮交付都附带「lint / test / build 全过」的结论。
Claude 的验收**从不引用这些结论**，而是：

1. 自己重跑 `npm run lint` / `npx vitest run` / `npm run build`
2. 自己重算对方报告里的每一个关键数字
3. 写**独立的对抗测试**（自己的 RNG、自己的 Solver、自己的取样脚本）

这不是不信任，而是**两个独立实现互相校验**才有意义。
实践中它抓出过真问题（见 §5）。

### 1.2 量化门槛：验收标准必须可判定

每轮改动前先定**数字门槛**，而非「看起来更好」：

```
❌ 「图案要更大一些」
✅ 「图案主体占卡牌 62%~68%，且不越 tile_frame 的 206px 安全区」
```

门槛写进文档 → Codex 实现 → Claude 逐条核对。
争议自然消解，因为双方对着同一个数字。

### 1.3 反向验证：**确认测试真的会红**

这是本项目最有价值的一条纪律。

新增防回归测试后，**故意把代码改回错误版本**，确认测试变红，再还原。
没做这一步的测试可能是「测了空气」——本项目实际发生过：

> M2 时我写的 Solver 剪枝交叉验证，复制了**错误的**剪枝逻辑，
> 结果在随机盘面上 0 个 mismatch——**这个测试根本没有鉴别力**。
> 后来改用 Python 穷举找到 3 个真实反例才证明问题。

### 1.4 分轮交付：结构与视觉分开

R2 拆成 R2-0（结构）+ R2-A（材质）分两次验收，**不合并**。
理由：结构改动的风险在布局与命中区，视觉改动的风险在参数数量，
混在一起出问题时无法定位。

### 1.5 争议处理：数据说话，谁对听谁的

本项目发生过 **3 次实质性技术争议**，全部以实测数据收场（§5）。
**三次全部是 Claude 判断有误、Codex 正确**。记录在案不是为了归咎，
而是这几次都改进了最终方案。

## 3. 设计阶段 `[Claude]`

### 3.1 从 V0.1 到 V0.3.4

初版 V0.1 由 GPT-5.6 生成，经四轮修订定稿。Claude 在设计阶段的主要贡献：

**发现并修正 §9.2 的数学错误（V0.2）**

我最初断言「4 种类型 + 7 格暂存槽 = 不可能失败」。**这是错的**：
`4 × 2 = 8 > 7`，四种类型每种放 2 张就已经溢出。
正确结论是**只有 3 种类型才绝对安全**（`3 × 2 = 6 < 7`）。

这个修正改进了设计——L1/L2 因此确定用 3 种类型，
新手前两关**数学上不可能失败**，符合休闲定位。

**难度阈值的三次教训**

**V0.3.3** 把难度门槛定得比测量噪声还窄（「目标 ±3pp」+ 严格单调），
导致构建在未见过的随机种子上随机失败
（「从 0.211 降到 0.205」= 0.6pp = 纯噪声）。
**V0.3.4 是删除该规则的修正版**，最终方案即出自 V0.3.4：

```
A. L1~L5 greedy ≤5%；L6~L20 ≤35%     （唯一硬性失败条件）
B. rate[i+1] >= rate[i] - 5pp         （容差 > ±4pp 的差值噪声）
C. avg(L6~10) < avg(L11~15) < avg(L16~20)   （分段均值）
— 删除「目标 ±3pp」硬门槛
```

**教训（后来又犯了两次，见 §5.2）**：
**定阈值前必须先算出该阈值在目标方案下的实际取值。**

### 3.2 冻结的接口契约

设计阶段定死、全程未违反：

1. `core/` 与 `config/` **零 Phaser 依赖**
2. `core/rules/` 是 GameModel / Solver / Simulator 的**规则单一真源**
3. 随机统一走 `SeededRandom`，**禁止 `Math.random()`**
4. `strict: true`，**不写 `any`**
5. 关卡数据必须过 Schema 校验
6. 素材路径**只走 Asset Manifest**

**上线时四条红线全部零违反**（§7 复查确认）。

## 4. Claude 的关键技术贡献 `[Claude]`

### 4.1 手机端 DPR 模糊修复（唯一由 Claude 实现的代码）

**用户反馈**：「字体很模糊，图片也不清晰」

**根因**：Phaser 的 `Scale.RESIZE` 把 canvas 像素缓冲设成 **CSS 尺寸**，
iPhone DPR=3 时等于让浏览器把整个画面**拉伸 3 倍**。

**为什么是「文字比图片更明显」**：卡片是圆润插画、色块平缓，糊一点不易察觉；
**文字笔画是高对比边缘，一拉伸立刻发虚**。用户的描述顺序精准指向了根因。

**这是第二次踩同一个坑**——garden 项目上线后收到过一模一样的反馈，
其 `main.ts` 至今留着注释「用户实测反馈的『字体很模糊』就是这个」。
StackPop 从零搭建时没沿用该方案，于是重蹈覆辙。

**修复**：`Scale.NONE` + `zoom: 1/scale` + 物理像素缓冲，**倍率封顶 2x**
（3x 屏是 9 倍填充率，老机器掉帧）。新增 `uiScale.ts` 换算层，
布局**先按 CSS 求解再整体放大**（直接喂物理像素会撞上 `tileSizeMax` 上限）。

**验证**：`buffer 750×1624 / CSS 375×812 = ratio 2.000`，
6 列 ground truth `52.17 / 44.34` **逐位未变**，11 项布局单测一行未改即全过。

**已固化**：写入长期记忆；`eslint-rules/requireScaledFontSize.js` 强制
场景字号必须走 `fontPx()` / `px()`（Codex 补充实现）。

### 4.2 UI 问题的量化诊断

三轮 UI 精修的**问题定位**均由 Claude 完成，且都是**先测量后判断**：

| 轮次 | 诊断 | 关键数据 |
|---|---|---|
| R1 | 图案被代码二次缩小 | 素材 68% × 渲染 0.70 = **实际只占 47.6%**，低于策划要求的 62~72% |
| R2-0 | 空白是结构问题不是氛围问题 | 残局最大单块空白 **占屏 54%**，没有背景美术能解决半屏空白 |
| R3 | 弹窗系统未跟上棋盘 | R2-A 只更新了 `drawToolButton`，弹窗用的是另外两个方法 |

其中 R2-0 那次，Codex 原方案把空白归为「氛围 / MA4 可选」，
Claude 通过模拟一局从开局到残局的空白变化（22% → 54%）证明它是**结构问题**，
并改判到材质精修**之前**执行——因为 HUD 与 Tray 的材质参数依赖周围留白，
顺序反了要重调一遍。

### 4.3 独立验收探针

除逐条核对门槛外，Claude 另写了独立探针，全部通过：

- **20 关初始盘面全部可解**（Solver 穷举，200k 节点预算）
- **打乱后仍可解**（抽样）
- **撤回栈有上限**（300 步长对局后 ≤120）
- **美术资源逐张验证**：解析 WebP 头比对尺寸/Alpha、测量图案 bbox 占比、
  检测抠图残留与边缘 fringing、计算两两亮度差与色相差

### 4.4 发布与部署纪律

- 每次部署**先 `--dry-run` 确认影响范围**，再实跑
- 部署后核对**本地与线上 md5 逐字节一致**
- 修改共享 nginx 配置时：先备份 → 确认规则唯一 → `nginx -t` 通过才
  `reload`（graceful）→ **逐个验证 9 个站点均 200**（含不归本仓库管的 mimo / mystock）
- 打 tag 前三项前置检查：工作区干净、测试构建全绿、两端 0 落后
- Tag 说明必须写清「**做完了什么、明确没做什么、怎么回滚**」——
  回滚点的价值在于半年后还知道它是什么

## 5. 三次技术争议与结论 `[Claude]`

**这一节是本文档最有价值的部分。** 三次争议全部以实测数据收场，
**三次都是 Claude 判断有误、Codex 正确**——这个比分本身就说明
「不采信报告」这条纪律必须双向适用，不能只用在对方身上。

### 5.1 Solver 剪枝：Codex 对 ✅

**争议**：Claude 在 V0.2 §12.4 指定按**列顶牌类型**去重剪枝。
Codex 指出应按**整列内容**去重。

**结论**：Claude 用 ~4000 个盘面的 Python 穷举交叉验证——
按顶牌去重产生 **5 个假阴性**（把可解盘面判为不可解），按整列内容 **0 个**。
**Codex 是对的**，实现按整列内容：

```ts
const signature = column.join(',');   // 不是 column[column.length - 1]
```

**附带发现**：Claude 最初写的交叉验证测试**复制了错误的剪枝逻辑**，
在随机盘面上 0 mismatch——**这个测试没有鉴别力**。
这直接催生了 §1.3 的「反向验证」纪律。

### 5.2 R2-0 门槛：Codex 对 ✅

**争议**：Claude 定「深度 2 时空白 ≤25%、深度 8→2 差值 ≤10%」。
Codex 复算指出严格居中下两条**无法同时成立**。

**结论**：Claude 复核确认——实测深度 2 是 **27.15%**、差值 **16.29%**，
两条都不达标。**Codex 完全正确。**

**Claude 的错误**：这两个数是**按感觉定的，没有先算一遍能否成立**——
与 §3.1 的难度阈值是同一类错误，**第三次**。

**但 Codex 的替代提法也需修正**：它建议改成「上下空白差 ≤1px」，
但这测的是「是否居中」而非「空白是否可接受」，实测恒为 `0.00`，
**永远不会红，等于没有门槛**。

最终方案分成三条：最大单块空白 ≤28%（深度 1 放宽到 30%）、
上下差 ≤1px、**且相对旧算法必须减半**（实测各深度恰好 −50%，这才是真正的收益指标）。

> 后续 Claude 又发现自己连「≤28%」也没算全——深度 1 是 29.87%，
> **同一轮里犯了第二次**。已修正为分档门槛。

### 5.3 失败弹窗「打乱」是否为 bug：Codex 对 ✅

**争议**：Claude 在 R3 建议中把 `GameScene.ts:771` 的
`'打乱', false` 判定为「硬编码禁用的 bug」，因为弹窗文案写着
「撤回一步，**或重新整理牌面**」，却点不动。

**Codex 反驳**：失败态 tray 已满 7 格，而打乱**只重排 columns、不动 tray**，
启用后依然无法取牌。

**结论**：Claude 构造真实的 `tray = 7/7` 失败态实测：

```
findSolvableShuffle(...) → 抛 SafeStateUnavailable
  'Current tray cannot be rescued by any next pick'
```

**打乱在该局面下连一个合法结果都产生不了。**
按 Claude 的建议改，会做出一个「可点击但必然失败」的伪功能——比禁用更糟。
**Codex 是对的。**

**Claude 的错误**：只读了按钮那一行代码，**没回到 `core/` 验证启用后
功能是否真的成立**。

**但问题的实质确实存在**——文案在引导一个做不到的操作。
Codex 的修法与 Claude 相反且更正确：失败页只保留**真实可执行**的
「撤回 / 重来」，并新增 `shuffle.test.ts:70` 锁死该不变量
（Claude 反向验证过：去掉 throw 该测试立刻变红）。

**固化的纪律**：
> 提「某处禁用是 bug」之前，先验证启用后功能是否真的成立。
> 只看 UI 层的 `enabled` 参数不够，要回到 `core/` 跑一遍。

## 6. 美术流程 `[Claude 验收部分]`

美术由 Codex 用 Image Gen 分四批产出，Claude 逐批量化验收。

### 6.1 批次纪律

`MA0 Master Reference（定风格）→ MA1 前 4 个 Tile → MA2 后 4 个 + 背景 → MA3 UI + FX`

**不跳批**。MA0 的作用是把风格定死——若 MA1 发现风格不对，
只需重画 4 张而不是 23 张。实践中该纪律严格执行，未出现返工。

### 6.2 Claude 的量化验收

| 批次 | 关键发现 |
|---|---|
| MA0 | 图案占框 **~85%**，超出工单要求的 68% → **要求 MA1 改回 68%**（后来证明这个要求是对的，见下） |
| MA1 | 67.97% 达标；棋盘格抠图**残留仅 1px**，边缘是暖棕描边色而非灰边 |
| MA2 | 三条亮度约束全达标；另发现**最小亮度差不在 Codex 汇报的对上**——是 `paw`/`fish`（ΔL=2.4），靠宽高比 1.04 vs 1.93 分离 |
| MA3 | `tile_frame` 安全区实测 **206px**，容得下 174px 图案 |

**MA0 那条 68% 要求后来成了关键**：R1 修复「图案被二次缩小」时，
正因为素材是按 68% 做的，才能直接把渲染倍率改成 `1.00` 得到规格占比，
**不必重画任何素材**。

### 6.3 意外收获：色盲可玩

MA2 验收时 Claude 做了**灰度 32px 测试**——完全去色后，
八类图案仅凭剪影仍可区分。这意味着色盲玩家可正常游玩。

该特性已写入工程红线，后续调色不得破坏。

## 9. Codex 视角的执行记录 `[Codex]`

### 9.1 策划案的演进 `[Codex]`

这七个版本节点不是普通的文案润色，而是依次修正了**玩法模型、工程边界、物理可行性、
产品难度和统计门禁**。如果直接按 V0.1 开工，后面的 Solver、20 关数据和 UI 都会建立在
错误规则上。

| 版本 | 主要变化 | 修改原因与实现影响 |
|---|---|---|
| **V0.1** | 定义竖向牌堆、顶部取牌、三消、撤回、打乱、20 关和分阶段开发；但采用 **3 格 Tray**，且只有 3 格全同才消除，否则直接失败；棋盘按 8 列设计 | 工程骨架已有可复用价值，但玩法实际退化为“必须连续点出三张同类”。不同类不能暂存，因而不存在本品类应有的“槽位压力—三消释放”循环；Solver 也错误地把一次动作理解为取一组三张 |
| **V0.2** | Tray 改为固定 **7 格**，任意三同随时消除；MVP 改为 6 列；Solver 动作改为逐张 Pick 且 Tray 进入状态；增加随机玩家模拟、无限 Undo 和边界规则 | 这一版修正了玩法本体。只有把 Tray 纳入状态，Solver 才能搜索“先取不同类、以后再补齐”的真实解法。但 V0.2 仍留下顶部 type 去重、`number[][]` solution、Hint 读取旧 solution、主线程 Shuffle 搜索、单一 save version 等实现风险 |
| **V0.3** | 合并 Codex Review 的 5 个 P0、5 个 P1 和 4 个 P2：完整列去重、逐步 solution、规则单一真源、三 Bot、Worker、双版本存档、多端与部署规范；同时冻结接口契约并明确 M0~M6 | V0.2 解决了“游戏是什么”，V0.3 解决“怎样实现才不会在模块间漂移”。文档从策划说明升级成了**可执行契约**：每阶段有输入、输出、门禁和明确禁区，代码评审可以检查引用、依赖、随机源和数据格式，而不是靠解释实现意图 |
| **V0.3.1** | 最大深度 10 → **12**，L20 从 90 张降为 **63 张**；增加 `tileCount <= columnCount * maxDepth * 0.88`；目标局长从 130s 调为 **85s** | M3 开工前复算发现 `6×10=60`，而原 L11~L20 多达 66~90 张，物理上装不下。深度 12 在 360×800 等四个视口仍保持 Tile 不被压缩；88% 上限又为列高参差、策略空间和生成器排布留下余量 |
| **V0.3.2** | 产品定位改为休闲：L1~L5 Greedy ≤5%，L6~L20 ≤35%；L3 顶部同类数 ≤2；难度旋钮由“换 seed”改为 **`depthSpread` 1~2 + seed 微调** | 固定“7 类/60 张/6 列/深 12”只换 12 个 seed，失败率仍为 87%~100%；而 spread 0~1 为 0%~11%、spread 2 为 13%~39%、spread 3 为 29%~85%。这说明 seed 只能微调，三张同类的深度差才决定槽位压力。原 70% 门槛也只能排除灾难关，不能保证休闲体验 |
| **V0.3.3** | 每策略采样数 **200 → 1000**；生成目标下移到 L6~L20 的 8%~30%，35% 只作为红线 | N=200 的单点噪声约 ±6.6pp，L13/L16/L17/L19 贴着 34% 时，换 trial seed 会随机越过 35%。增至 1000 后约 ±2.9pp，并让生成目标与红线保留约 5pp 边际 |
| **V0.3.4** | 删除“目标值 ±3pp”构建门禁；逐关单调增加 **5pp 容差**；新增 `avg(L6~10) < avg(L11~15) < avg(L16~20)`；稳定校验改为随机 5 个 trial seed 或显式指定 | N=1000 时两点差值噪声约 ±4pp，±3pp 和严格单调都比噪声窄，未见 seed 会把合格关卡随机判失败。最终把 `levelCurve.ts` 的目标值留作生成器搜索方向，只让休闲红线、带容差趋势和分段均值进入构建门禁 |

V0.3 引入接口契约和 Stage 划分的依据是**返工半径**。依赖顺序被固定为：

```text
M0 布局与工程可行性
  → M1 纯规则
    → M2 搜索 / 随机 / 撤回 / 模拟
      → M3 关卡数据
        → M4 渲染、动画与美术
          → M5 持久化
            → M6 外部部署
```

高风险且可纯函数验证的内容前置，昂贵且依赖前置状态的内容后置。M1 若没有先证明“不同类可共存”，
M2 的 Solver 会搜索错误状态；M2 若没有先稳定，M3 的 20 关会成为不可验证数据；布局若拖到 M4
才验证，正式美术和动画都会跟着返工。V0.3 因此冻结了四类可机器检查的边界：

1. `core/`、`config/` 不依赖 Phaser，规则可在 Node/Vitest 中直接运行。
2. 随机只走 `SeededRandom`，Snapshot 必须带 `rngState`，问题才能复现和撤回。
3. 关卡 JSON、solution、Asset Manifest 和 Save Schema 都有显式版本或校验器。
4. 每个 Stage 只进入约定范围；例如 M1 不先做美术，M3 不改 20 关规格，M6 不碰站点根。

### 9.2 M0~M6 各里程碑的实现细节 `[Codex]`

#### M0：骨架与布局可行性

M0 建立 Vite + TypeScript strict + Phaser + Vitest/ESLint 骨架，以及 Boot、Preload、Home、Game
四个 Scene。这里没有把布局当作 M4 的视觉问题：先用色块覆盖 4 个手机 viewport、3 档
`OVERLAP_RATIO`、3 个桌面 viewport 和 896×414 横屏触屏。

关键决策是让 `calculateGameLayout()` 成为无 Phaser 的纯函数，横向尺寸与纵向预算一起求解；
桌面采用限宽居中，横屏提示必须同时满足横屏和 coarse pointer，不能只按宽度判断。1280×700
首轮截图发现 Tray 标题没有计入纵向预算，深棋盘几乎贴到标题。修正后深度 10 保留 **14px**
间距，`tileSize=49.51px`，仍高于 48px 下限，因此把桌面最小高度冻结为 700px。

M0/M1 合并验收时，手机覆盖 375×812、390×844、430×932、360×800；桌面覆盖
1920×1080、1440×900、1280×700。这个阶段最后确定 `OVERLAP_RATIO=0.85`，后续的
6 列 ground truth `tileSize=52.17 / rowStep=44.34` 因而可以长期作为回归基准。

#### M1：纯规则原型

M1 只做 `core/rules/` 的四个纯函数：`canPick`、`resolveMatches`、`applyPickToState`、
`checkStatus`。`applyPickToState` 返回新状态而不修改入参；列数组末位始终是顶部；Tray 按 type
分组插入，每次 Pick 后立即消除三同并紧凑。Scene 只负责把输入交给 Model、再根据状态绘制。

固定验收夹具同时覆盖三条不同路径：

- Path A：12 步清空，最终 `columns=[0,0,0,0,0,0]`、`tray=[]`、`status=won`。
- Path B：依次取不同类仍继续游戏，7 步后 `tray=[watering]`，证明没有退回 V0.1 规则。
- 失败路径：7/7 后锁输入，Restart 恢复列高、Tray 和步数。

M0+M1 当时为 **3 个测试文件、20 项测试**。先把规则链路锁死，再进入 Solver，是为了让搜索、
模拟和真人游戏共享同一个可验证的状态转移。

#### M2：Undo、随机、Solver、Shuffle 与 Simulator

M2 是整个项目的最高风险阶段，实际拆成五个相互约束的部件。

**1. Snapshot 与确定性随机。** `UndoManager.ts:17-37` 的 Snapshot 保存 columns、Tray、
moveCount、combo 和 `rngState`；恢复状态时保留当前工具使用次数并增加 `undoUsed`。内存历史上限
为 **120**，M5 持久化只保留最近 **5** 步。`SeededRandom.ts:11-37` 使用 xorshift32，
Fisher-Yates 也由同一 RNG 驱动；因此同一 seed 可重放，Shuffle 后 Undo 还能恢复随机序列，
全库无需 `Math.random()`。

**2. Solver 搜索。** `Solver.ts:128-168` 是深度优先搜索，找到第一条解即返回逐步
`SolutionStep[]`；没有把一次三消伪装成一个动作，每个分支只 Pick 一张。动作按去重后的列索引
顺序遍历，没有再叠一套启发式排序；这里需要的是确定性的存在性证明和第一条可重放解，而不是
求“最优解”。剪枝顺序是：

- 空列且 Tray 空时成功；Tray 达 7 或任一类型总数不能被 3 整除时立即失败。
- `hashState()` 对**完整列字符串排序**，Tray 也排序，消除左右列顺序和 Tray 分组顺序造成的
  状态重复；已确认死路放入 `deadStates`。
- 同一节点只跳过**完整内容相同**的列；`Solver.ts:103` 的签名必须是
  `column.join(',')`。顶部同为 paw 但底部为 bell/fish 的两列会暴露不同后继，不能合并。

构建期默认预算是 **2,000,000 节点**，运行时 Shuffle 降到 **200,000 节点**
（`config/tuning.ts:28-31`）。前者用于离线 20 关验证，没有逐帧响应约束，优先减少误判；后者
只用于运行时 Shuffle，并由外层 400ms 墙钟超时再兜底，避免把构建期最坏搜索成本带到主流程。
超过预算抛 `SolverBudgetExceeded`，不返回 `false`；否则“预算不足”会被静默记录成“关卡不可解”。
仓库回归用 200 个 seeded 可达局面，把完整列剪枝与完全不做
对称剪枝的 DFS 逐例对拍；Claude 的独立穷举规模约 4000 个局面，另找出顶部剪枝的 5 个
假阴性，二者是不同层次的证据。

**3. 规则单一真源。** 只要求“调用相同逻辑”仍可能在未来被复制一份后悄悄分叉，因此代码
把引用直接导出：`SOLVER_APPLY_PICK`、`SIMULATOR_APPLY_PICK`、`SIMULATOR_CAN_PICK`、
`LEVEL_APPLY_PICK`。测试不是比较两个实现的结果，而是用 Vitest `toBe()` 断言它们分别与
`core/rules/applyPickToState` / `canPick` **引用相等**。这使 Solver、Simulator 和 solution
replay 一旦改成自写规则，测试会在行为差异出现前就失败。

**4. Shuffle 与 Worker。** 随机候选必须保持 Tile ID、类型计数、列高和当前 Tray 不变，
每个候选再把当前 Tray 一起交给 Solver。Worker 最多尝试 **50 次**；随机搜索失败时，
`generateSafeState()` 先补 Tray 中已有的 pair/single，再按完整 triple 排取牌序列，反向回填
原列高并再次过 Solver。主线程客户端设置 **400ms** 超时，超时或 Worker error 都终止线程，
走无需搜索的确定性安全构造。取舍是：Worker 与序列化增加了一个独立 chunk（当时 7.38KB）
和回退代码，但避免了 DFS 卡住点击与动画；实测随机 Shuffle 14ms 时主线程仍有 9 个 event-loop
tick。运行时只在 Shuffle 做求解，不把 Solver 放进普通点击路径。

**5. Simulator。** Random、Greedy、Cautious 三个 Bot 都从共享 `canPick` 取得合法动作，再用
共享 `applyPickToState` 推进。Greedy 优先补三、补二、可见三同；Cautious 在此基础上按
Tray 类型数、Tray 长度、新类型惩罚、消除奖励和暴露牌支持度打分。输出不只含 failRate，还含
`avgMaxTray`、`p95MaxTray`、最大不同类型数和平均步数。M2 最终为 **9 个测试文件、53 项测试**；
固定 12 张夹具的 Greedy/Cautious 均为 0% 失败，Random 为 37%。

#### M3：20 关、生成器与难度曲线

M3 加入 JSON `LevelLoader` 和 20 关：L1~L5 保持手工序列，L6~L20 由生成器产出。
`LevelGenerator.ts:12-30` 先建立三张一组的 TileGroup 和一条天然可清除的 Pick 顺序；
`findBatchSchedule()` 再用回溯把每组分配到列深，约束同组最大深度差不超过
`targetDepthSpread`；最后把列反转成运行时“数组末位为顶部”的格式，并把每步的
`columnIndex + expectedTileType` 写入 solution。这样生成器给出构造性解法，Solver 再提供
独立的存在性验证。

校验分四层：Schema/计数/深度与 **88% 容量**、Solver 可解、solution 逐步重放防数据漂移、
Simulator 难度。集合级校验另外锁住 L1/L2 的 `3×2<7`、L3 初始顶部同类 ≤2，以及图案类型
台阶只能落在 **L6/L10/L17**。

难度调优经历了两次方向修正：第一次发现原 L11~L20 连物理容量都不满足，先完成 V0.3.1
的规格重算；第二次是 V0.3.2 放弃只搜索 seed，改用 `depthSpread` 决定大区间、seed 决定
区间内微调。随后 200→1000 次采样降低噪声，V0.3.4 又把生成目标与构建红线拆开。
`validate-levels:stable` 默认用 `node:crypto` 随机取 5 个 seed，也允许评审方传入自己的 seed，
避免只在实现方挑选的 17/137/911 上通过。

最终规格保持 20 关的类型/张数/列/深度不再变化，只调排布；L20 为 7 类、63 张、6 列、
深 12、目标 85s。M6 发布门禁仍报告 20/20 Schema、数量/深度、Solver、solution 和难度曲线
通过。

#### M4：正式 UI、交互、多端与美术接入

M4 先用同名同尺寸占位资源把运行时契约做完，再由 MA 批次直接覆盖文件，代码不随画稿变化。
`config/assets.ts` 同时充当加载与渲染清单；测试要求 `PRELOAD_ASSETS` 的每个纹理 key 都出现在
`RENDERED_TEXTURE_KEYS`，防止“首屏下载了但从未绘制”的静默浪费。

交互上实现 Tile 跳跃、Tray 位移/紧凑、三消粒子、7 格满摇晃、胜负弹窗、桌面 hover/cursor、
限宽居中和只针对触屏横屏的旋转提示。`InputQueue` 在一个动画执行时最多保留 **2 个待处理点击**，
重复点同一列会在出队时重新读取顶部；win/fail/restart/undo/shuffle/shutdown 六个状态都显式
`clear()`，防止旧输入穿过场景或状态切换。

音效没有创建第二个 `AudioContext`，而是 `adoptContext(this.sound.context)` 复用 Phaser 已解锁的
WebAudio Context；这条约束来自 iPhone 静音的既有事故。纹理、音效、输入生命周期和横屏条件
均有契约测试。M4 + MA1 交付时测试达到 **76 项**，首批正式图案可直接替换占位资源。

#### M5：关卡选择、存档、设置与星级

M5 增加 20 关选择、解锁、最好星级、继续游戏、音乐/音效/震动设置，以及每次 Pick、Undo、
Shuffle、Restart 后的中途保存。`SaveManager` 的关键不是“写 localStorage”，而是把兼容性拆成
两个版本维度：

- `saveSchemaVersion` 描述整个 `PlayerSave` 结构。JSON 损坏或版本不兼容时回到默认存档，
  因为旧结构无法安全解释。
- `levelRevision` 只描述当前关卡盘面。它不匹配时，`SaveManager.ts:123-159` 只让
  `currentRun=null`，仍保留解锁进度、历史最好星级和 Settings；改一关不应清空玩家总进度。

读取路径逐字段解析 `unknown`，校验 TileType、列数、Tray 容量、数值范围、状态、重复 Tile ID
和最多 5 个持久化 Snapshot，不对 `localStorage` 内容做类型断言。`getItem`/JSON 失败返回默认值，
`setItem` 失败只被捕获，游戏继续使用内存中的状态；隐私模式或配额异常不能中断一局游戏。
通关只提高星级不降低历史最好值，并解锁下一关。M5 验收为 **13 个测试文件、83 项测试**，
浏览器刷新后可恢复 columns、Tray、步数和 Undo 栈。

#### M6：子目录部署

M6 把 Vite 生产 base 固定为 `/stack/`，先用本地 production preview 验证 HTML、哈希 JS 和
Worker 子目录路径，再编写默认 dry-run 的 `deploy.sh`。发布前门禁依次执行 test、
`validate-levels`、simulate、lint、TypeScript 和 Vite build；同步完成后脚本自动比较本地/远端
`index.html` MD5 并检查线上 HTTP 200。

首次上线只写 `/www/wwwroot/g.ismayday.mobi/stack/`，没有增加站点根入口。远端文件归属
`www:www`，文件 644、目录 755/2755；首次发布的本地/远端 MD5 都是
`75a3c698bbbe52603ca32e59bdcd11c9`。发布时完成 PC 首页、进入首关和合法取牌冒烟；iPhone
真机验收被明确保留为外部门槛，后来也正是它发现了 DPR 模糊，证明桌面冒烟不能替代真机。

### 9.3 美术生成流程 `[Codex]`

美术实际交付是 **22 张游戏资源 + 1 张不投放的 Master Reference**。流程没有一次性生成整包，
而是 MA0→MA1→MA2→MA3 逐批冻结风格、几何和运行时契约。

**Prompt 策略。** MA0 先生成 2×2 的 paw/grass/watering/bell 风格表，只定义圆润块面、暖棕描边、
统一高光、奶油底框和 32px 可辨性；初稿铃铛多出铃舌，采用 precise-object-edit，只允许删除
铃舌，明确其余三图、布局、颜色和阴影全部不动。MA0 实测图案占框约 85%，所以它只作为风格
参照，不能作为生产几何参照。

MA1/MA2 改为**每个图案单独生成**，共同 Prompt 固定“256×256、仅图案、真正透明、最长边约
68%、无奶油底框、无文字/水印/额外物件、32px 可辨”，每张再追加轮廓与禁项。例如 watering
必须是横向突出的壶嘴/把手，bell 不得有铃舌，yarn 必须近圆且不能形成 paw 的放射轮廓。
MA3 的 UI/FX 继续引用 Master 风格，但成对资源用编辑模式：`tray_slot_warn` 只改普通槽边沿，
`panel_fail` 只改胜利面板色调，从源头保持几何一致；按钮明确只画 icon，文字由代码渲染。

**棋盘格烘焙处理。** Image Gen 多次声称透明，但返回的是把棋盘格烘进 RGB、没有有效 alpha
的图。直接按颜色全局删除会同时误删 bone、鱼眼和主体高光；重新生成又可能丢失已确认造型。
最终采用机械提取：从画布边缘识别与边缘连通的中性棋盘底，只删除这一个背景区域，保留被
主体轮廓包围的白色；再取前景 bbox、等比缩放到最长边 **174px**、亚像素居中、生成 alpha
并转 WebP。Tray/Panel 这种成对资源不按各自 bbox 裁切，而是沿完整原画布同尺度处理，以免
普通/预警、胜/负两态切换时跳动。该流程只用于离线资产加工，没有进入运行时代码。

机械处理之后不是凭肉眼放行：MA1 四张合计只检出 **1px** 中性灰残留，半透明抗锯齿边缘
占 2.7%~5.5%，边缘均值仍是暖棕而非灰边；MA2 四张为单一连通主体、灰残渣 0px。八张 Tile
的最长边均为 174px（67.97%），居中偏移 ≤0.5px。

**分批自检。** 每批交付前都生成实际尺寸证据，而不是只看 256px 原图：

- MA0：四格各约 32px，1 秒内能否靠轮廓区分。
- MA1：单张 32px + 四张并排 32px，并叠真实 `tile_frame` 在 52px 真机尺寸复核。
- MA2：八图彩色 32px、灰度 32px和冲突对；使用 Rec.709 mean L 验证 bone−fish=66.6、
  bell−flowerpot=75.7，两张 1125×2436 背景只有 10.9KB/11.6KB且中央低对比。
- MA3：`tile_frame` 中央安全区实测 205~206px，174px 图案每边仍约有 15.5px 余量；
  Tray 48px、按钮 72px、sparkle 22px/star 72px、Panel 240×270 分别合成；12 张 UI/FX
  都是单一 RGBA 前景。22 张投放图片合计约 **173KB**。

**BGM。** 源 `windy.mp3` 为 104.00s、MP3 320kbps、4,168,855B，首约 1.43s、尾约 5.68s
静音，整曲约 −15.1 LUFS。选取 **00:09.567~00:43.445** 的 33.878s 主体：它比
01:01.463~01:24.079 候选更舒缓，和声与能量首尾更接近，且不抢三消音效。末尾和开头做
**350ms 等功感交叉淡化**后，有效循环为 33.528s；保持 44.1kHz 双声道，整体降低约 6.09dB，
输出目标约 −22 LUFS：M4A 96kbps 为 409,486B/−21.9 LUFS，MP3 128kbps 为
537,561B/−22.3 LUFS。

加工时 `-map_metadata -1` 清除源 metadata，再只写通用标题；发布文件不含 artist、album 或
网易 `163 key` comment。M4A 优先可少传约 24%，MP3 兜底。BGM 不进入 `PreloadScene`：首页
先渲染，常驻 `BackgroundMusicScene` 默认 **800ms 后**独立加载，若用户先点击则立即加载，
音乐设置为关时完全不请求。冷页面实测 DOMContentLoaded 227ms、window load 326ms、BGM
请求 1181ms 开始/1601ms 完成，晚于首屏 load 855ms，期间没有 >50ms Long Task。

### 9.4 部署与运维 `[Codex]`

`deploy.sh` 的核心不是 rsync，而是让 `--delete` 的危险范围在执行任何安装、构建或网络写入前
就被证明正确。`deploy.sh:23-45` 有三条硬断言：目标不能等于站点根；目标必须**精确等于**
`$REMOTE_ROOT/stack`，兄弟目录也不接受；Vite base 必须是 `/stack/`。`DRY_RUN` 只能是 0/1，
默认 1。之所以不用“只要以 root 开头就允许”，是因为 `/garden/` 同样在 root 下，而它不属于
本项目权限范围。

同步前执行完整门禁，构建后再确认 `dist/index.html` 存在。rsync 虽带 `--delete`，但已经被
精确子目录断言包住；dry-run 先展示新增/删除清单，实际发布后统一 755/644 并对齐 `www:www`。
MD5 和 HTTP 200 是脚本的终止条件，不是人工观察项。M6 还分别反向测试了站点根、garden 目录
和错误 base，三种配置都在写入前被拦截。

首次上线暴露了一个脚本边界之外的性能问题：共享 nginx 的 30 天图片规则原先只包含
`gif|jpg|jpeg|png|bmp|swf`，WebP 没有 `Cache-Control`，22 张图每次重传。经额外授权后，
操作顺序是：备份为 `g.ismayday.mobi.conf.bak-webp-20260823`；确认目标 location 和
`server_name` 各自唯一；只追加 `svg|ico|webp`；`nginx -t` 通过才 graceful reload；最后逐个
验证共享配置下 **9 个站点**仍为 200。结果为 `max-age=2592000`。

BGM 上线又发现音频扩展名不在该缓存规则中，400KB 音频会重复下载。第二次只追加
`mp3|m4a|ogg|wav`，沿用同一备份/语法检查/9 站复验纪律。代价是资源替换不能再依赖同名覆盖：
图片或音频内容变化必须使用 `v2` 等新文件名，否则用户可能在 30 天内继续命中旧文件。

### 9.5 Codex 视角：与 Claude 协作的体会 `[Codex]`

#### 真正提高了质量的评审

1. **V0.2 对玩法模型的修正价值最高。** 3 格改 7 格、单张 Pick、Tray 入 Solver 状态不是参数
   调整，而是把一个错误品类模型改成可玩的 Triple-Match。若这一步晚于代码，M1~M3 会整体作废。
2. **独立真值对拍比普通单测有效。** 完整列去重的争议不能靠多写几个同实现测试解决；约
   4000 个盘面与无剪枝 DFS 的独立对拍给出了 5/0 的证据。仓库随后保留 200 个 seeded 回归，
   一边负责发现，一边负责长期门禁。
3. **把视觉意见转成可测几何。** 68% 图案、206px 安全区、R2 空白占比、DPR 缓冲比、
   52.17/44.34 ground truth，都比“再精致一点”更适合实现和回归。尤其 R2-0 把半屏空白从
   氛围问题改判为结构问题，避免继续用背景细节掩盖布局缺陷。
4. **复验外部状态。** dry-run、MD5、9 站 HTTP、真机截图矩阵分别覆盖代码测试碰不到的发布
   边界、共享配置和设备差异。iPhone 的 DPR 事故证明这类复验不是形式工作。

#### 定得不合理或一度帮倒忙的门槛

需要直说：并非所有“量化门槛”都提高了质量，**没有先做可行性计算的数字比没有数字更危险**。

- V0.3 最初的 L6~L20 ≤70% **偏松**。它能拦灾难关，却允许 L12=51%、L17=66%、L18=62%
  这种休闲游戏不应出现的曲线；第一次 M3 虽然“通过”，产品目标没有通过。
- V0.3.3 的“目标 ±3pp + 逐关严格单调”**偏严且统计上错误**。N=1000 单点噪声约 ±2.8pp、
  差值约 ±4pp，门槛本身比噪声窄；它造成未见 trial seed 上 0/20 的随机构建失败，并消耗一轮
  关卡调优去解决其实不存在的数据问题。V0.3.4 删除该门禁才是正确处理。
- R2-0 的 ≤25% 和 8→2 差值 ≤10% **在所选严格居中算法下物理不可达**；修订后的 ≤28%
  又漏算深度 1 的 29.87%。这不是实现精度问题，而是验收方没有在下发前把公式代入全域。
- R3 把失败弹窗的禁用 Shuffle 判成一行 bug，属于**会制造伪功能的评审意见**。Tray 已 7/7，
  Shuffle 又被规则限定不能改 Tray，只启用按钮必然抛 `SafeStateUnavailable`。最终应改文案和
  操作集合，而不是迎合 UI 表象。
- M4 的一部分契约测试只扫描源码字符串，能挡住直接写 `new AudioContext()`，但挡不住
  `webkitAudioContext` 或别名构造；作为早期门禁可以，不能把它当运行时证明。截图矩阵从 M4
  拖到 R2-A 才补齐，也说明首轮 UI 验收**偏松**。

#### 三次争议时我的判断依据

三次争议最终都是实现侧结论成立，但依据不是“代码是我写的”：

1. **Solver 列去重**看状态等价关系。只有两列的整个剩余序列相同，Pick 后后继状态才同构；
   顶牌相同只说明当前拿到的 type 相同，不说明下一张相同。因此签名必须覆盖整列。
2. **R2-0 门槛**看约束方程。把 402×773、Tile 高、rowStep 和深度代入 `slack/2`，即可在动代码
   前证明深度 2 是 27.15%，无需靠截图争论。但我提出的“上下差 ≤1px”只证明居中，不能证明
   空白改善；Claude 要求再加“相对现状改善 ≥45%”是必要补充。
3. **失败 Shuffle**看核心不变量和可达状态，而不是按钮参数。失败定义是 Tray 满；Shuffle
   保持 Tray 不变；`canPick` 在 Tray 满时拒绝所有列。三个条件连起来已经构成不可能性证明，
   再用 `SafeStateUnavailable` 的真实测试锁定边界。

#### 协作流程应怎样改

1. **门槛进入开发前先做 preflight。** 几何门槛要列出最坏 viewport/深度并代入；统计门槛要写
   N、置信区间和差值噪声；功能建议要给出一个 core 层成功用例。做不到的先标“观察项”，
   不得直接变 build fail。
2. **分开“生成目标”和“验收红线”。** `targetGreedyFailRate` 可以指导搜索，但不能因为 29%
   测成 32% 就让构建失败。目标负责优化，红线负责拒绝，两者容差来源不同。
3. **评审先检查不变量，再检查 UI 调用点。** 对 enabled/disabled、恢复、撤回、打乱等状态功能，
   评审必须从 `core/` 状态转移走到 Scene；只读最后一行参数容易得出相反结论。
4. **独立复验仍应保留，但要避免共享同一错误。** 最有效的是不同语言/不同算法/不同 seed 的
   真值探针，并对新增测试做一次故障注入；复制生产逻辑再跑一遍不构成独立证据。
5. **实现方必须有门槛否决义务。** “评审定标准、实现方只执行”在标准自相矛盾时会浪费时间。
   更合理的流程是评审方提出产品红线，实现方先完成可行性复算，双方确认后再冻结。
6. **设备与状态矩阵应在对应 Stage 当轮补齐。** DPR>1、Tray 5/7/6/7、胜负、确认弹窗、
   1280×720 不应拖到上线后。自动测试守逻辑，截图/真机矩阵守最终呈现，二者不能互相替代。

## 10. 经验总结 `[Claude 起草，Codex 补充]`

### 10.1 有效的做法 `[Claude]`

1. **不采信报告，全部自己重跑** —— 两个独立实现互相校验
2. **量化门槛** —— 把「更好看」翻译成可判定的数字
3. **反向验证** —— 确认测试真的会红，否则可能测的是空气
4. **分轮交付** —— 结构与视觉分开，出问题能定位
5. **争议以数据收场** —— 三次争议全部实测解决，**三次都证明 Claude 错**
6. **批次纪律** —— 美术先定风格再铺量，避免大规模返工
7. **实现方有门槛否决义务** —— 三次争议里两次是实现方先做可行性复算
   才拦住了自相矛盾的标准。「评审定标准、实现方只执行」在标准本身
   有问题时会浪费整轮工时

### 10.2 踩过的坑 `[Claude]`

1. **同一个坑栽两次** —— garden 已解决过 DPR 模糊，StackPop 重蹈覆辙。
   **跨项目经验必须固化成可检索的记录**，否则等于没有。
2. **桌面验收挡不住移动端问题** —— DPR bug 在 DPR=1 上根本不存在，
   94 项单测全绿、构建通过、线上 200 全部无效。
   **移动端问题必须有可量化的检查**，而非肉眼看截图。
3. **定阈值前不先算** —— 本项目最反复的一个错误，且**两个方向都犯过**：
   - **偏松**：V0.3 最初的「L6~L20 ≤70%」只能拦灾难关，
     放过了 L12=51% / L17=66% / L18=62% 这种休闲游戏不该有的曲线。
     第一次 M3「通过」了门槛，但产品目标没通过。
   - **偏严**：V0.3.3 的「±3pp + 逐关严格单调」比测量噪声还窄
     （N=1000 单点噪声 ±2.8pp、差值 ±4pp），造成未见 seed 上的随机构建失败，
     还白白消耗一轮关卡调优去解决根本不存在的数据问题。
   - **算不全**：R2-0 门槛在所选算法下物理不可达；修订后的 ≤28%
     又漏算了深度 1 的 29.87%。

   Codex 的总结很准确：**没有先做可行性计算的数字，比没有数字更危险**。
   前者会把团队引向错误方向并消耗真实工时，后者至少还停留在讨论层面。
4. **换算层漏乘不报错** —— `px()` 漏一处不会崩，只是元素小一半。
   已用 ESLint 规则固化。
5. **只看 UI 层判断功能是否可用** —— §5.3 的教训。

### 10.3 对后续项目的建议 `[Codex + Claude]`

**Claude 部分**：
- 新起 Phaser 项目**直接照抄 DPR 方案**，不要等用户反馈
- 从第一天就建立「量化门槛 + 反向验证」的验收闭环，
  成本远低于后期返工
- **跨项目的踩坑记录必须可检索**——本项目两次栽在同一个坑上，
  代价是一次线上事故

**Codex 部分（实现方视角）**：

- 开工第一天先冻结**纯状态模型、随机源和模块依赖方向**，再做 Scene；Rule/Solver/Simulator
  应通过函数引用或依赖注入证明共享同一真源，不能只靠文档约定
- 里程碑按返工半径排序：布局可行性 → 规则 → 搜索/生成 → 数据 → 视觉 → 存档 → 部署；
  不要在规则和布局尚未证明前批量生产关卡或美术
- 所有随机过程必须可传 seed、输出 seed，并区分“生成 seed”和“测量 trial seed”；
  随机门禁必须声明样本量、噪声和容差
- 把生成器的**优化目标**与 CI 的**拒绝红线**分开。目标可以窄，红线必须只拦产品不可接受的结果
- UI 项目尽早抽出共享 Button/Panel/Animation lifecycle；同一视觉语义若有三套绘制函数，
  后续每轮精修都会漏一套
- 部署脚本只允许写**精确子目录**，默认 dry-run；`--delete`、共享 nginx、站点根和跨项目配置
  都必须各自有显式边界断言和发布后验证
- 从 M0 建立真实设备与状态截图矩阵，并把 DPR、safe-area、横竖屏、满槽、弹窗等可量化项
  固化为测试；不要用桌面 DPR=1 或单张空状态截图替代移动端验收
- 静态资源一旦设置长缓存，内容更新就换版本化文件名；Asset Manifest 同时作为加载、渲染和
  体积测试的单一入口，避免代码路径和 CDN 缓存各自演化
