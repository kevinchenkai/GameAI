# StackPop UI 进一步美化建议（Claude，2026-08-24）

> 前置：R1 / R2-0 / R2-A 已全部验收并上线，iPhone 真机验收通过。
> 依据：R2-A 截图矩阵（`output/playwright/ui-r2-a/`）+ 源码复核。
> 性质：**当前 UI 已达可上线水准**。以下是「从可用到好看」的建议，
> 供 Kevin / Codex 讨论后决定取舍，不是缺陷清单。

---

## 0. 先说结论

R2 把**棋盘区**做到了很高完成度：图案占比恢复、底部基线、严格居中、
covered/active 层次、Tray 危险态。真机验收通过是应得的。

但**弹窗系统没跟上**。截图矩阵一拉出来，差距很明显：

| 区域 | 完成度 |
|---|---|
| 棋盘 / Tray / 工具栏 | R2-A 已精修 ★★★★☆ |
| **胜负弹窗 / 确认弹窗** | **仍是 R1 之前的水平 ★★☆☆☆** |

原因在代码里很清楚：R2-A 统一按钮材质时只改了 `drawToolButton`，
而弹窗用的是另外两个方法（`drawResultButton` / `drawConfirmationButton`），
**没被一起更新**。详见 [CodeReview §2](./CodeReview_整体_Claude_20260824.md)。

所以本文第一优先级不是「加特效」，而是**把弹窗拉到和棋盘同一水准**。

## 1. P0｜失败弹窗的「打乱」被写死禁用（功能缺陷，非美化）

**这条不是美化建议，是 bug，建议单独优先修。**

`GameScene.ts:771`：

```ts
this.drawResultButton(left + buttonWidth + gap, buttonTop, buttonWidth,
  '打乱', false, 'secondary', () => void this.performShuffle());
//          ↑ 硬编码 false，永远禁用
```

对比工具栏的同一功能（`GameScene.ts:558`）：

```ts
playing && remainingShuffles > 0   // 正常按剩余次数判定
```

### 后果

玩家 Tray 满 7 格失败时，弹窗文案写着**「撤回一步，或重新整理牌面」**，
**但「打乱」是灰的、点不动**——即使他还剩 3 次打乱没用。
文案在引导一个做不到的操作，玩家会认为按钮坏了。

### 建议

```ts
const remainingShuffles = GAMEPLAY.shuffleLimit - state.shuffleUsed;
this.drawResultButton(..., '打乱', remainingShuffles > 0, 'secondary', ...);
```

若产品意图确实是「失败后不允许打乱」，那**文案必须改**，
不能提「重新整理牌面」。但我倾向允许——本作定位是轻松休闲，
失败时给一条自救路径更符合「低压力」的产品调性。

**验收门槛**：剩余打乱 >0 时该按钮可点且能真正打乱；=0 时禁用且样式与
`disabledFill` 一致。

## 2. P0｜弹窗按钮与工具栏材质不一致

### 现象

看 `mobile-win-dialog` / `mobile-fail-dialog` 截图：

- 三个按钮**同宽、同色、扁平、无阴影**
- 底部工具栏的按钮有圆角、描边、阴影、按压态
- **同一屏里两套按钮语言**

### 根因

三处按钮各自实现（CodeReview §2）。R2-A 只升级了其中一处。

### 建议

抽公共 `RoundedButton` 后，弹窗按钮自动继承 R2-A 的材质。
**同时修正主次层级**——当前三个按钮视觉权重相同，但语义完全不同：

**胜利弹窗**

| 按钮 | 建议权重 |
|---|---|
| **下一关** | **主按钮**（最宽、实心黄、有阴影）——这是 95% 玩家要点的 |
| 再玩一次 | 次级（描边、浅底） |
| 选择关卡 | 三级（文字按钮或最窄） |

**失败弹窗**

| 按钮 | 建议权重 |
|---|---|
| **撤回一步** | **主按钮**——最低成本的自救 |
| 打乱 | 次级（且必须按 §1 修好） |
| 重新开始 | 三级 + **弱化**（破坏性操作，丢整局进度） |

> 「重新开始」目前是 `danger` 变体，但视觉上并不比另外两个弱。
> 破坏性操作应当**更难点到**，而不是同样醒目。

## 3. P1｜胜利时刻缺少庆祝，与策划案不符

### 策划 §5.1 明确写了

```
最后三消 → 0.3s 停顿 → 星星/彩纸 → 胜利弹窗
```

### 现状

代码里 `drawResult()` **直接画弹窗**，没有停顿、没有彩纸、
星星也是静态出现（`setTint` + `setAlpha` 而已，无入场动画）。

胜利是整局唯一的正反馈时刻，现在它和失败弹窗一样「啪」地弹出来，
情绪落差被抹平了。这是**当前 UI 与策划案差距最大的一处**。

### 建议（三档，按成本递增）

**A. 最低成本（纯代码，无新素材）** — 推荐先做这档
1. 最后一次三消后 **停顿 300ms**（策划已写明）
2. 弹窗 **scale 0.8 → 1.0 + Back.easeOut**，180ms
3. 三颗星 **依次弹入**，各延迟 120ms，`Back.easeOut` + 轻微超调
4. 复用现有 `fx/sparkle_01`、`sparkle_02`、`star` 三张已有素材，
   在星星位置各放 6~8 个粒子向上飘散

**素材已经在库里了**（MA3 第 3 批产出，`fx/` 三张），
但目前**只在三消时用过**，胜利时完全没用上——等于白做了。

**B. 中等成本**：加彩纸（confetti）粒子从顶部落下，2 秒
**C. 高成本**：新增庆祝音效 + 星级逐颗计数音

### 验收门槛

- 胜利动画总时长 ≤1.2s（休闲游戏不该让人等）
- 可跳过：动画期间点击直接跳到终态
- **不阻塞** `settled → READY_FOR_INPUT` 的状态机契约

## 4. P1｜背景在棋盘区仍然过淡（R2-B 的重新评估）

D4 当初决定「暂不重画背景，先降代码 wash」。R2-0 收回一半空白后，
现在可以重新判断了。

### 实测

R2-A 截图里棋盘区背景仍接近纯色渐变，`game_bg` 的猫咪水印
位置偏下、几乎看不见。空白虽然减半，但**剩下的部分依然是「空」而不是「景」**。

### 建议：不重画，改用「分层视差」

不需要开 MA4 工单重画背景。现有素材就能改善：

1. 把 `game_bg` 的云层与地面**拆成两个图层**（或直接在代码里加几个
   半透明圆角矩形当远景云）
2. 棋盘区上方留白处放 **1~2 朵极淡的云**（alpha ≤0.25），
   随棋盘居中位置**极缓慢**移动（视差感）
3. 猫咪水印**上移**到棋盘区与 HUD 之间的留白中心

> ⚠️ 关键约束：任何背景元素 **alpha 不得超过 0.3**，
> 且**不得进入棋盘卡片的正后方**——R2-A 好不容易做出的
> covered/active 27 点亮度差，很容易被花哨背景吃掉。

如果这档做完仍嫌单调，**再**考虑开 MA4 重画。

## 5. P2｜HUD 信息可以更有「游戏感」

当前 HUD 是「第4关 / 步数 5 / 剩余 36 张 / ⚙」，信息正确但偏报表。

建议（成本很低）：

- **剩余牌数加进度条**：一条极细的横条（2~3px）贴在 HUD 底边，
  按 `已消除 / 总数` 填充。玩家能一眼看到「快通关了」——
  这是**当前完全缺失的进度感**
- 数字 `36` 变化时**跳一下**（scale 1.2 → 1.0，120ms），
  给消除一个额外的正反馈落点
- 「步数」在休闲定位下不是玩家关心的指标，可考虑降级为更小字号，
  把视觉权重让给「剩余」

---

## 6. P2｜取牌手感的两个小增强

真机验收通过说明基础手感没问题，以下是锦上添花：

1. **顶牌轻微呼吸**：每列可点牌 `scale 1.0 ↔ 1.015`，周期 2s，
   相位随列错开。让「可点」在静止画面里也能被感知
   （现在只有阴影和暖沿，是静态线索）
2. **落位缓冲**：牌进 Tray 时加一点 `Back.easeOut` 超调，
   现在是 `Quad.easeOut`，偏「工整」而不「弹」

> 两条都要能被「减少动态效果」系统设置关闭（§7）。

---

## 7. P3｜可访问性：补 `prefers-reduced-motion`

R2-A 已守住「非仅靠颜色表达状态」和「灰度 32px 可辨」两条，很好。

缺的一条：**系统「减少动态效果」未被尊重**。
若采纳 §3 / §6 的动画建议，前庭敏感玩家会不适。

```ts
const reduceMotion = window.matchMedia('(prefers-reduced-motion: reduce)').matches;
```

`reduceMotion` 为真时：跳过庆祝粒子、呼吸动画、超调缓动，
保留必要的位置变化但缩短到 ≤80ms。

## 8. 建议顺序与取舍

| # | 项 | 类型 | 优先级 | 成本 |
|---|---|---|---|---|
| 1 | **失败弹窗打乱按钮写死禁用** | **功能 bug** | **P0** | 极低（一行） |
| 2 | 弹窗按钮统一材质 + 主次层级 | 一致性 | **P0** | 低（依赖 CodeReview §2 的 `RoundedButton`） |
| 3 | 胜利庆祝动画（A 档） | 情绪 | P1 | 中（复用已有 fx 素材） |
| 4 | 背景分层视差 | 氛围 | P1 | 中 |
| 5 | HUD 进度条 + 数字跳动 | 进度感 | P2 | 低 |
| 6 | 顶牌呼吸 / 落位缓冲 | 手感 | P2 | 低 |
| 7 | `prefers-reduced-motion` | 可访问性 | P3 | 低，但做 3/6 就必须一起做 |

**建议 R3 只做 1 + 2 + 3。**

理由：1 是 bug；2 和 CodeReview 的 `RoundedButton` 重构是同一件事，
一次做完；3 是当前与策划案差距最大、且情绪收益最高的一项，素材还是现成的。

4~7 留到 R4，或视真机手感再定。

## 9. 工程红线（沿用，不重复论证）

1. 不改关卡数据、Tile 尺寸、布局算法、命中区
2. 6 列 ground truth **52.17 / 44.34** 逐位不变
3. 新增尺寸一律走 `px()` / `fontPx()`
4. 材质参数进 `GAME_UI`，不散落在场景
5. covered/active 亮度差**不得低于 20 点**（R2-A 实测 27）
6. 灰度 32px 八类图案仍可辨
7. 动画不得阻塞 `READY_FOR_INPUT` 状态机契约
8. 若新增背景素材，**文件名必须升版本号**（线上 30 天缓存）
9. 完成后 lint / test / build 全绿 + 真机截图矩阵复验

# 10. 更正与 R3 验收（Claude，2026-08-24）

## 10.1 §1「失败弹窗打乱是 bug」—— **我错了，Codex 是对的**

我把 `GameScene.ts:771` 的 `false` 判定为「硬编码禁用」，**结论错误**。

Codex 指出：失败态 tray 已满 7 格，而打乱**只重排 columns、不动 tray**，
因此打乱后依然无法取牌。我实测验证：

```
构造 tray = 7/7 的真实失败态
findSolvableShuffle(...) → 抛 SafeStateUnavailable
                            'Current tray cannot be rescued by any next pick'
```

**打乱在该局面下连一个合法结果都产生不了。** 若按我的建议改成
`remainingShuffles > 0`，会做出一个「可点击但必然失败」的伪功能——
比禁用更糟。

**我的错误在于**：只读了按钮那一行代码，**没有回到 `core/` 验证该操作在
失败态下是否真的可执行**。判断一个禁用是不是 bug，必须先确认
「启用之后功能是否成立」——我跳过了这一步。

**Codex 的处理方式是对的**：不盲从评审意见，先回核心规则验证，
再新增 `shuffle.test.ts:70` 把该不变量锁死。我反向验证过——
去掉那句 throw，该测试立刻变红，不是空气。

文案侧它也处理了：失败弹窗现在只显示**真实可执行**的「撤回 / 重来」，
不再出现「或重新整理牌面」这种引导做不到的操作的文案。**问题的实质
（文案与可用操作不符）确实存在，只是修法与我说的相反。**
