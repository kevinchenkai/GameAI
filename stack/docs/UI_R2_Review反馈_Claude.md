## 0. 总体结论

**R2 方案的四个组件族方向正确，但优先级排错了一项。**

R2-1~R2-4（卡片层次、按钮材质、Tray 细节、HUD 材质）**都是对的**，我没有异议，
可以按方案执行。

**但 R2-5「背景留白」被归为「氛围 / R2-B / MA4 可选」是错误的分类。**
它不是氛围问题，是**布局结构问题**，且严重度高于全部四项材质问题。
详见 §1。

## 1. 必须改判：R2-5 不是氛围问题，是结构问题

### 1.1 实测数据

R2 文档把 HUD 与牌堆之间的空白归因为「背景主题感偏弱」，建议靠提高背景对比度缓解。
**这个归因不成立。**

我按截图实测可视区 402×773、6 列，模拟一局从开局到残局的空白变化：

| 最深列 | 棋盘顶 y | HUD 下方空白 | 占屏幕 |
|---:|---:|---:|---:|
| 8（开局） | 261 | 168px | **22%** |
| 7 | 303 | 210px | **27%** |
| 4 | 429 | 336px | **43%** |
| 2（残局） | 513 | 420px | **54%** |

**残局时超过半屏是空的。** 没有任何背景美术能解决半屏空白——
提高背景对比度只会让「一大片显眼的空背景」更显眼。

### 1.2 根因（代码级）

`GameLayout.ts:165`：

```ts
const baselineY = layout.trayTop - Math.max(0, spaceBeforeTray) - layout.tileSize;
```

`baselineY` **恒等于 Tray 上方固定位置**，与实际列深无关。
因此列越短，棋盘整体越靠下，**所有余量单向堆积在 HUD 与棋盘之间**。

这与 R1 之前的问题**同源**：R1 前空白在棋盘下方，R1 后空白搬到了棋盘上方，
**总量一点没减少**，只是换了位置。

### 1.3 为什么必须在材质精修之前做

1. **影响面**：残局占半屏，是整个界面最大的单一视觉缺陷；
   四项材质问题加起来影响的像素面积也不及它。
2. **返工风险**：HUD（R2-4）与 Tray（R2-3）的材质、阴影、边距，
   都依赖它们**周围有多少留白**来判断是否协调。
   先精修材质、再改结构，材质参数要重调一遍。
3. **成本低**：`calculateCenteredBoardTop` **已经写好了**
   （`GameLayout.ts:141`），目前**只被自己的测试引用**，生产代码不再调用。
   可直接复用。

## 2. 建议的 R2 执行顺序

### R2-0（新增，最先做）：回收 HUD 与棋盘之间的空白

**目标**：棋盘整块在 `boardTop ~ trayTop` 之间垂直居中，
**保留 D3 的列内底部对齐**（可点牌仍逐位对齐成一条线）。

即：列内基线不变，但**整块棋盘作为一个整体上移**，空白平分到上下两侧。

实现建议：

```ts
// calculateBottomAlignedBoardPlacements 内
// 现在：baselineY 恒定贴 Tray
const baselineY = layout.trayTop - spaceBeforeTray - layout.tileSize;

// 建议：baselineY 由实际最深列决定，使整块棋盘居中
const maxDepth = Math.max(1, ...columnDepths);
const contentHeight = layout.tileSize + (maxDepth - 1) * layout.rowStep;
const areaTop = layout.boardTop;
const areaBottom = layout.trayTop - spaceBeforeTray;
const slack = Math.max(0, (areaBottom - areaTop) - contentHeight);
const baselineY = areaBottom - layout.tileSize - slack / 2;
```

`calculateCenteredBoardTop` 的居中算法可直接复用，不必重写。

**跳动问题**：整块棋盘会随最深列变化而移动。若实测觉得跳，
用 §12.2 已批准的**分档**思路（档位 `[2,4,6,8,10,12]`，跨档才重排 + 200ms tween），
不要逐层平移。

#### R2-0 量化门槛

| # | 门槛 | 判定 |
|---|---|---|
| 1 | 402×773 / 6 列，最深列 2 时，HUD 下方空白 **≤ 25% 屏高** | 单测计算 |
| 2 | 最深列 8 与最深列 2 的空白差 **≤ 10% 屏高**（不再单向堆积） | 单测计算 |
| 3 | 每列可点 Tile **仍逐位对齐同一条基线** | 现有 `layout.test.ts` 断言不得改动 |
| 4 | 6 列 ground truth **52.17 / 44.34** | 逐位相同 |
| 5 | 命中区与渲染坐标**仍出自同一函数** | 源码检查 |
| 6 | 反向验证：改回恒定 baselineY 时门槛 1、2 **变红** | 必做 |

> ⚠️ §12.2 要求底部基线**独立可回滚**。R2-0 只改 `baselineY` 的计算方式，
> 不改列内对齐语义，回滚面更小——这条要求继续有效。

### R2-A（其后）：R2-1 ~ R2-4 四项材质精修

**方案照批，无修改意见。** 但要求：

- 所有新增尺寸继续走 `px()` / `fontPx()`
- 材质参数（圆角 / 描边宽度 / 阴影透明度 / 各状态填充）**写进 `GAME_UI` 常量**，
  不要散落在场景里——R1 的 `toolButtonStyle.ts` 是好范例，继续沿用该模式
- disabled / enabled 的**视觉 token 分离**已在 R1 建立，新组件必须遵循

### R2-B：背景

**同意暂不重画**（D4 决定不变）。R2-0 完成后重新看真机截图再定——
很可能空白收回后，现有背景就够用了。

## 4. 关于 Figma

**建议不做。**

R1 已经证明「量化门槛 + 代码常量 + 真机截图」这套闭环是有效的：
8 条门槛逐条可判、反向验证能确认测试有效、真机截图给主观判断兜底。

材质精修同样可以用**参数表**描述（圆角 12/16、描边 1.5px、阴影 alpha 0.18……），
比视觉稿更容易验收，也不会引入一份**需要与代码同步的额外真相源**——
视觉稿一旦与代码脱节，反而会成为争议来源。

如果某个具体效果确实说不清（例如卡片投影的具体观感），
**贴一张离线合成的 before/after PNG 就够了**，不需要完整 Figma 文件。

# 7. 门槛修正（Claude，2026-08-23 第二版）

## 7.1 Codex 是对的，我的门槛算错了

Codex 复算指出严格居中下无法同时满足门槛 1、2。**我复核后确认它完全正确。**

402×773 / 6 列，严格居中实测：

| 深度 | 上空白 | 占屏 | 上下差 |
|---:|---:|---:|---:|
| 8 | 83.95px | 10.86% | 0.00 |
| 4 | 167.91px | 21.72% | 0.00 |
| 2 | 209.88px | **27.15%** | 0.00 |

- 门槛 1（深度 2 ≤25%）：实际 **27.15%**，不达标
- 门槛 2（8→2 差值 ≤10%）：实际 **16.29%**，不达标

**我的错误**：这两个数我是**按感觉定的，没有先算一遍**能否成立。
这是我在 V0.3.3 / V0.3.4 定难度阈值时犯过两次的同一类错误——
**定阈值前必须先算该阈值在目标方案下的实际取值**。第三次了，记在这里。

## 7.2 但 Codex 的门槛 2 提法也需要修正

Codex 建议门槛 2 改为「每个深度下上下空白差 ≤1px」。
**这条测的是「是否居中」，不是「空白是否可接受」**——它恒为真（实测全是 0.00），
无法在空白过大时报警，等于没有门槛。

两者要分开：

- 「是否居中」是**实现方式**，值得断言，但它自动成立
- 「空白是否可接受」是**用户可感知的结果**，必须独立设限

## 7.3 修正后的门槛（以此为准）

| # | 门槛 | 目标值 | 依据 |
|---|---|---|---|
| 1 | **最大单块空白**（上下取大者）占屏 | **≤ 28%** | 严格居中实测最坏 27.15%，留 0.85pp 余量 |
| 2 | 上下空白差 | **≤ 1px** | 验证「确实居中」（Codex 提法，采纳） |
| 3 | 最大单块空白**相对现状必须减半** | 各深度 ≥45% 改善 | 见下表，这才是本轮的实际收益 |
| 4 | 每列可点 Tile 仍逐位对齐同一基线 | 现有断言不得改 | 不变 |
| 5 | 6 列 ground truth 52.17 / 44.34 | 逐位相同 | 不变 |
| 6 | 命中区与渲染坐标同出一函数 | 源码检查 | 不变 |
| 7 | 反向验证：改回恒定 baselineY 时门槛 1、3 变红 | 必做 | 不变 |

门槛 3 的依据（最大单块空白）：

| 深度 | 现状 | 居中后 | 改善 |
|---:|---:|---:|---:|
| 8 | 22% | 11% | −50% |
| 4 | 43% | 22% | −49% |
| 2 | 54% | **27%** | −50% |

**结论：采用「严格居中」，不加位移上限。** 回答 Codex 的问题。

理由：位移上限会让棋盘在某些深度既不贴 Tray 也不居中，是第三种无法解释的状态；
而严格居中把最大单块空白**在每个深度都砍掉一半**，收益已经足够。

## 7.4 更深一层的根因（R2-0 不解决，但必须记录）

复核时发现空白的真正来源**不止 baselineY**：

```
可用区 93 ~ 604，高 511px  ← 按 maxDepth=12 预留
L4 实际配置深度 8，内容高 343px
→ 开局就多出 168px = 22% 屏高，与取牌无关
```

`calculateGameLayout` 按 `maxDepth`（此处 12）预留棋盘区，
而 `trayTop` 锚定在**视口底部**（`toolsTop - sectionGap - traySlotSize`），
不随实际深度上移。**所以总 slack 是布局阶段就定死的，居中只能重新分配、无法回收。**

若要真正回收，需要让 `trayTop` 随关卡配置深度上移——
但这会改变 `calculateGameLayout` 的契约，**触碰 6 列 ground truth 52.17 / 44.34**，
风险远高于 R2-0，且会影响全部 20 关的布局。

**决定：R2-0 不动这一层。** 先拿居中的一半收益，
若真机看仍嫌空，再单独开一轮评估「Tray 随配置深度上移」，
届时必须重新确认 ground truth 与全部 20 关的可用性。

## 7.5 给 Codex 的结论

1. **采用严格居中**（`slack / 2`），不加位移上限
2. 门槛以 **§7.3 表格**为准，作废 §2 的原门槛 1、2
3. 门槛 3（相对现状减半）是本轮真正要保住的收益，**必须写成测试**
4. §7.4 的深层根因**本轮不处理**，但请在代码注释里标注，避免日后重复排查
