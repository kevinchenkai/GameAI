# H5《萌宠叠叠消》游戏策划与 Codex 执行方案 V0.1

> 文档用途：作为产品策划、玩法规则、关卡配置、程序架构、美术规范和验收标准的统一输入，可直接交给 Codex / Claude Code 开始实现。  
> 参考方向：用户提供的竖屏 H5 小游戏截图。  
> 项目暂定名：**萌宠叠叠消 / Pet Stack Match**。后续可随时替换名称与主题。  
> 目标平台：移动端 H5，优先适配 iPhone / Android 浏览器，并为后续微信小游戏、抖音小游戏移植预留接口。

---

## 0. 一句话定义

一款 **“竖向卡牌堆叠 + 只取最上层 + 三枚同类消除 + 少量临时槽 + 撤回/打乱辅助”** 的轻度益智 H5 小游戏。

核心体验不是传统交换式 Match-3，而是：

> **观察当前各列最上方的图案 → 找出可组成三枚同类的组合 → 依次取出 → 自动三消 → 暴露下一层 → 直到清空棋盘。**

单局目标时长约 1～4 分钟，操作只需要点击，适合移动端碎片化体验。

# 1. 项目目标

## 1.1 产品目标

首版重点不是做大而全，而是验证以下体验：

1. **3 秒内看懂玩法。**
2. 点击反馈清晰，卡片“跳”到收集区的动画有爽感。
3. 玩家能够通过观察和短期规划解决棋盘，而不是完全依赖随机。
4. 一局足够短，可以自然形成：
   - 再来一局；
   - 下一关；
   - 失败后立即重试。
5. 项目结构足够干净，方便后续快速增加：
   - 新主题；
   - 新图案；
   - 新关卡；
   - 新障碍；
   - 广告复活；
   - 微信/抖音小游戏 SDK。

---

## 1.2 MVP 范围

首版必须实现：

- 竖屏 H5；
- 主页；
- 关卡选择；
- 游戏主场景；
- 8 列式棋盘；
- 顶部可操作卡片判定；
- 3 个收集槽；
- 三枚同类自动消除；
- 胜利 / 失败；
- 撤回；
- 打乱；
- 重新开始；
- 20 个配置关卡；
- 本地进度保存；
- 基础音效和动画；
- 移动端适配。

首版暂不做：

- 登录；
- 后端；
- 排行榜；
- PvP；
- 复杂养成；
- 强制插屏广告；
- 大量皮肤；
- 云存档。

# 3. 核心玩法规则

## 3.1 棋盘结构

默认：

```text
columnCount = 8
```

每列是一组从下向上堆叠的 Tile。

例如：

```text
Column 0:
[PAW, GRASS, CAN, PAW, BELL]

Column 1:
[GRASS, CAN, BELL]
```

数组下标 0 表示最底部。

**数组最后一枚 Tile 为当前列最上方、可操作 Tile。**

---

## 3.2 Tile 类型

MVP 建议 6 种：

```text
paw       猫爪
grass     小草
watering  浇水壶
bell      铃铛
bone      骨头
fish      小鱼
```

第一批关卡只使用前 4 种，避免一开始信息量过大。

---

## 3.3 可点击规则

任何时刻：

- 每列只有最上方 Tile 可以点击；
- 被其他 Tile 压住的 Tile 不可点击；
- 空列不可点击；
- 动画执行期间暂时锁输入。

可点击 Tile：

- 正常亮度；
- 点击时轻微上浮 / 放大。

不可点击 Tile：

- 不需要做成灰色；
- 只需不响应输入。

这样视觉上更干净。

---

# 4. 收集与三消

## 4.1 点击流程

玩家点击某列最上面的 Tile：

```text
1. 判断该 Tile 是否可点击
2. 从 Column 中移除
3. Tile 播放跳跃动画
4. Tile 进入底部 Tray
5. 检查 Tray 是否存在 3 个相同 type
6. 若存在 → 自动消除
7. 检查胜利
8. 检查失败
9. 解锁玩家输入
```

---

## 4.2 Tray 插入规则

MVP 推荐：

**按照点击顺序从左到右插入。**

例如：

```text
[PAW] [GRASS] [PAW]
```

玩家再点击 GRASS：

若容量允许，则继续插入。

但 MVP 容量为 3，因此：

```text
traySize = 3
```

推荐采用更清晰的规则：

> 玩家必须在 3 次选择内组成同类三枚。

即：

```text
[PAW] [PAW] [PAW]
→ 消除
→ Tray 清空
```

如果：

```text
[PAW] [GRASS] [CAN]
```

Tray 已满且没有三连：

```text
→ 本局失败
```

这个规则非常容易理解，也能形成“观察当前所有列顶部图案”的核心策略。

---

## 4.3 自动消除

满足：

```text
tray.length === 3
&&
tray[0].type === tray[1].type
&&
tray[1].type === tray[2].type
```

则：

```text
MATCH
```

播放：

1. 三枚卡片放大至 1.08；
2. 轻微弹跳；
3. 星光粒子；
4. 缩小 + Fade；
5. Tray 清空；
6. Combo +1。

总时长建议：

```text
320～450 ms
```

不要超过 600 ms，以免频繁三消时节奏拖沓。

---

# 5. 胜负规则

## 5.1 胜利

当：

```text
所有 columns 都为空
AND
tray 为空
```

判定胜利。

流程：

```text
最后三消
→ 0.3s 停顿
→ 星星 / 彩纸
→ 胜利弹窗
```

胜利弹窗：

- 第 X 关完成；
- 星级；
- 步数；
- 撤回次数；
- 下一关；
- 再玩一次。

---

## 5.2 失败

当：

```text
tray 已满
AND
无法组成三枚同类
```

进入失败。

失败界面：

```text
这一步卡住啦！
```

按钮：

- 撤回一步；
- 重新开始；
- 可选：观看奖励视频继续。

H5 MVP 中先不接真实广告。

程序预留：

```ts
RewardedAdProvider
```

开发环境使用 mock：

```text
点击后直接成功
```

# 6. 撤回系统

这是该玩法非常重要的体验功能。

## 6.1 设计原则

每次合法点击 Tile 前，保存一次完整状态：

```ts
GameSnapshot
```

至少包含：

```ts
{
  columns,
  tray,
  moveCount,
  combo,
  rngState
}
```

---

## 6.2 撤回

点击“撤回”：

```text
恢复上一个 Snapshot
```

动画：

- Tray 中的 Tile 倒飞回原列顶部；
- 或 MVP 直接用 180ms 状态过渡。

---

## 6.3 撤回限制

建议：

```text
免费撤回：每关 3 次
```

MVP 调试阶段：

```text
无限撤回
```

通过配置切换：

```ts
undoLimit: -1
```

表示无限。

# 7. 打乱系统

## 7.1 目的

避免某些局面玩家完全失去可解组合，同时给玩家“救场”手段。

---

## 7.2 MVP 打乱规则

只重新排列：

```text
当前棋盘中尚未消除的 Tile
```

保持：

- 列数不变；
- 每列当前高度不变；
- Tile 总数不变；
- Tray 不变。

步骤：

```text
1. 收集 columns 中全部 tile type
2. Fisher-Yates shuffle
3. 按原列高度重新填回
4. 校验是否至少存在一个当前可组成的三同类顶部组合
5. 如果不存在，最多重新 shuffle 50 次
6. 仍失败时，使用 solver 生成一个安全局面
```

# 9. 关卡设计

## 9.1 基本原则

所有 Tile 总数必须满足：

```text
totalTileCount % 3 === 0
```

而且每一种 Tile 的总数量最好也是：

```text
count(type) % 3 === 0
```

这样不会出现理论上无法全部消除的残留。

---

## 9.2 难度维度

难度主要由以下因素决定：

### 1. 图案种类

简单：

```text
3～4 种
```

困难：

```text
6～8 种
```

---

### 2. Tile 总数

```text
Level 1: 24
Level 10: 48
Level 20: 72
Level 50+: 90+
```

---

### 3. 列深

越深，需要提前规划越多。

---

### 4. 当前顶部可选项数量

顶部同类越集中：

```text
越容易
```

顶部图案越分散：

```text
越难
```

---

### 5. 强制步骤

某一时刻只有一种三连可行：

```text
forcedMove
```

可以很好地用于教学关卡。

---

### 6. 陷阱深度

玩家误选之后，需要撤回多少步才能恢复。

# 11. 关卡生成策略

首版不要完全随机生成。

**必须生成“已知可解”的棋盘。**

推荐使用：

> **逆向生成 + Solver 校验**

---

## 11.1 逆向生成思路

先生成一个必定能消除的“解题顺序”：

```text
AAA
BBB
CCC
AAA
DDD
...
```

每 3 个一组。

然后倒序将这些 Tile 分配到各列。

因为我们知道正确取牌顺序，所以理论上一定存在解。

---

## 11.2 生成步骤

伪代码：

```ts
function generateSolvableLevel(config) {
  const solutionGroups = createTripleGroups(config);

  const columns = createEmptyColumns(config.columnCount);

  for (const group of reverse(solutionGroups)) {
    distributeGroupIntoColumns(group, columns);
  }

  if (!solver.canSolve(columns)) {
    return generateSolvableLevel(config);
  }

  return columns;
}
```

---

# 12. Solver

关卡编辑与自动生成都应该配一个简单 Solver。

这是整个项目非常值得投入的模块。

## 12.1 状态

```ts
type SolverState = {
  columns: TileType[][];
}
```

由于正确玩法要求每轮选三个同类，因此可以把“一组三连”作为一次搜索动作，而不是逐张搜索。

---

## 12.2 可执行动作

统计所有列顶部：

```ts
Map<TileType, columnIndex[]>
```

任何满足：

```text
columnIndex.length >= 3
```

的 TileType 都是一种合法动作。

从对应列中任选三列，弹出顶部 Tile。

---

## 12.3 DFS + Memo

```ts
function canSolve(state): boolean {
  if (isEmpty(state)) return true;

  const hash = hashState(state);

  if (memo.has(hash)) {
    return memo.get(hash);
  }

  const moves = getTripleMoves(state);

  for (const move of moves) {
    const next = applyMove(state, move);

    if (canSolve(next)) {
      memo.set(hash, true);
      return true;
    }
  }

  memo.set(hash, false);
  return false;
}
```

为了防止组合爆炸：

- 对相同高度 / 相同顶部结构做 canonical hash；
- 设置最大节点数；
- 关卡生成阶段允许 50～200ms；
- 运行时提示优先使用预计算 solution。

# 13. 可解性保障

每个正式关卡 JSON 建议保存：

```ts
solution?: number[][]
```

例如：

```json
[
  [0, 2, 5],
  [1, 4, 7],
  [0, 3, 6]
]
```

代表：

```text
第一组：点第 0、2、5 列
第二组：点第 1、4、7 列
...
```

用途：

- QA 自动验证；
- 提示；
- 检测关卡数据被误改；
- 自动化回归测试。

# 19. 棋盘自适应布局

不要写死像素。

输入：

```ts
boardWidth
columnCount
gap
```

计算：

```ts
tileSize =
  (boardWidth - (columnCount - 1) * gap)
  / columnCount
```

约束：

```text
tileSize min = 54 CSS px
tileSize max = 92 CSS px
```

如果高度不够：

- 优先缩小 tile；
- 再缩小 rowGap；
- 不允许棋盘被底部工具栏遮挡。

# 31. 点击逻辑伪代码

```ts
async function onColumnTap(columnIndex: number) {
  if (model.status !== 'playing') {
    return;
  }

  if (!rules.canPick(model.state, columnIndex)) {
    return;
  }

  undoManager.push(model.snapshot());

  model.status = 'animating';

  const result = rules.pick(model.state, columnIndex);

  await animation.moveTileToTray(result.tile);

  if (rules.isMatch(model.state)) {
    await animation.playMatch(model.state.tray);

    model.clearTray();
  }

  if (rules.isWin(model.state)) {
    model.status = 'won';
    await showWin();
    return;
  }

  if (rules.isFail(model.state)) {
    model.status = 'failed';
    await showFail();
    return;
  }

  model.status = 'playing';

  saveSystem.save();
}
```

# 65. 最终建议

这类产品真正决定品质的不是规则复杂度，而是下面五件事：

1. **顶部信息是否一眼能读懂；**
2. **每次三消是否存在明确而舒服的反馈；**
3. **关卡是否真的可解而且难度自然增长；**
4. **误操作之后是否有合理恢复手段；**
5. **移动端是否始终流畅、按钮足够大、没有布局跳动。**

因此开发优先级应该是：

```text
规则正确
>
可解关卡
>
点击与消除手感
>
移动端适配
>
美术丰富度
>
商业化
```

首版只要把这条主链做到足够顺滑，就已经可以形成一款完成度很高的 H5 休闲小游戏。
