# 1. 一句话定义

一款 **「竖向卡牌堆叠 + 只取最上层 + 七格暂存槽 + 三枚同类自动消除 + 撤回/打乱辅助」** 的轻度益智 H5 小游戏。

核心体验不是传统交换式 Match-3，而是：

> **观察各列最上方图案 → 把有用的牌捞进暂存槽 → 槽位逐渐紧张 → 凑齐三枚自动消除、腾出空间 → 暴露下一层 → 直到清空棋盘。**

单局目标时长约 1～3 分钟，操作只需点击，适合移动端碎片化体验。

## 1.1 核心体验循环（本作的"爽点"定义）

这是 V0.2 新增的一节，也是理解全部规则改动的钥匙。

```
张力累积                          张力释放
─────────────────────────────►  ╱╲  ─────────►
槽位 2/7 → 4/7 → 6/7           砰！三消      槽位回到 4/7
"还剩一格了"                    "腾出来了"     "又能喘口气"
```

**这个「张力—释放」循环，是该品类唯一的核心快感来源。**

它完全依赖一个前提：**暂存槽可以存放不同类的牌**。玩家敢于先捞一张暂时凑不齐的牌，是因为他相信"后面还能补上"——这份"赌一把"的心理活动，就是玩法的全部乐趣。

> ⚠️ V0.1 的 3 格设计（必须连续三张同类，否则失败）把这个循环彻底删掉了。剩下的只有「猜对 / 猜错」，且第一次点错就出局，容错为零。这是 V0.2 首要修正项，详见 §4。

# 2. 项目目标

## 2.1 产品目标

首版重点不是做大而全，而是验证以下体验：

1. **3 秒内看懂玩法**（不读说明）。
2. 点击反馈清晰，卡片「跳」进暂存槽的动画有爽感。
3. 玩家能通过观察和短期规划解决棋盘，而非完全依赖随机。
4. 一局足够短，可自然形成：再来一局 / 下一关 / 失败后立即重试。
5. 项目结构足够干净，方便后续快速增加：新主题、新图案、新关卡、新障碍、广告复活、微信/抖音 SDK。

## 2.2 MVP 范围

**必须实现：**

- 竖屏 H5；主页；关卡选择；游戏主场景
- **6 列式棋盘**（V0.2 修正，见 §19）
- 顶部可操作卡片判定
- **7 格暂存槽**（V0.2 修正，见 §4）
- 三枚同类自动消除
- 胜利 / 失败
- 撤回；打乱；重新开始
- 20 个配置关卡
- 本地进度保存
- 基础音效和动画
- 移动端适配

**首版不做：** 登录、后端、排行榜、PvP、复杂养成、强制插屏广告、大量皮肤、云存档。

# 3. 核心玩法规则

## 3.1 棋盘结构

```text
columnCount = 6        // MVP 默认，关卡可配；8 列见 §19.3
```

每列是一组从下向上堆叠的 Tile。

```text
Column 0: [PAW, GRASS, CAN, PAW, BELL]
Column 1: [GRASS, CAN, BELL]
```

数组下标 0 表示最底部。**数组最后一枚 Tile 为当前列最上方、可操作 Tile。**

> 此约定全项目统一，不允许任何模块反转。JSON、Model、Solver、View 一致。

## 3.2 Tile 类型

MVP 定义 8 种（前 4 种用于早期关卡）：

```text
paw        猫爪
grass      小草
watering   浇水壶
bell       铃铛
fish       小鱼
yarn       毛线球
bone       骨头
flowerpot  花盆
```

第一批关卡只使用前 4 种，避免一开始信息量过大。

## 3.3 可点击规则

任何时刻：

- 每列只有**最上方** Tile 可以点击
- 被其他 Tile 压住的 Tile 不可点击
- 空列不可点击
- **暂存槽已满（7/7）时，所有 Tile 不可点击**（V0.2 新增，见 §5.2）

可点击 Tile：正常亮度，点击时轻微上浮 / 放大。
不可点击 Tile：不做灰色处理，只是不响应输入（视觉更干净）。

# 4. 暂存槽与三消 ★ 本版核心修正

## 4.1 槽位规格

```ts
traySize = 7        // MVP 固定 7，关卡可配
```

**为什么是 7：** 这是 Triple-Match 品类（《羊了个羊》《Triple Match 3D》系族）的行业标准值，经过大量产品验证：

- **少于 5**：容错太低，玩家不敢试探，退化为纯猜测
- **7**：可以暂存 6 张不同类的牌 + 1 张缓冲，压力感恰到好处
- **多于 8**：几乎不会输，张力消失

参考截图底部显示 **3 个空槽 + 1 个带 ▶️ 视频图标的槽**——那不是"总共 3~4 格"，而是**已用完的可视格 + 广告解锁的额外格**。原型图与 7 格规格并不冲突。

## 4.2 消除规则（与 V0.1 完全不同）

```text
每次有 Tile 进入 tray 后，立即检查：
  若 tray 中存在任意 type 的计数 >= 3
    → 消除该 type 的 3 枚
    → 其余 Tile 向左紧凑（保持相对顺序）
    → 可能连锁：消除后再次检查（理论上单次点击最多触发 1 次，但代码要写成 while）
```

关键差异：

| | V0.1 | V0.2 |
|---|---|---|
| 触发时机 | tray 满 3 格时才判定 | **每次插入后立即判定** |
| 判定条件 | 3 格**全部**同类 | **任意** type 计数 ≥ 3 |
| 不同类的牌 | 直接判负 | **正常暂存，等待补齐** |

## 4.3 Tray 排列规则

**按 type 分组排列，不是纯点击顺序。**

新 Tile 插入位置：

```text
若 tray 中已存在同 type 的 Tile
  → 插入到该组最后一个之后
否则
  → 追加到队尾
```

例：tray = `[PAW, GRASS, PAW]`（点击顺序 PAW→GRASS→PAW），实际显示为：

```text
[PAW] [PAW] [GRASS] [ ] [ ] [ ] [ ]
```

**为什么必须分组：** 让玩家一眼看清"我已经攒了 2 个爪子，还差 1 个"。若按点击顺序散乱排列，玩家需要逐格扫描计数，这是纯粹的认知负担，没有任何策略价值。这是该品类的通用做法。

插入时播放 100~140ms 的"挤开"位移动画，让分组过程可见。

## 4.4 完整点击流程

```text
 1. 判断 status === 'playing'
 2. 判断该列非空 且 tray 未满
 3. push GameSnapshot 到 undo 栈
 4. 从 Column 尾部移除 Tile
 5. Tile 播放跳跃动画 → 飞入 tray 目标槽位
 6. 其余 tray Tile 播放挤开位移
 7. while (存在某 type 计数 >= 3)：
      播放三消动画 → 移除该 3 枚 → 剩余左移紧凑
 8. 检查胜利
 9. 检查失败
10. 保存当前局面（中途恢复用）
```

## 4.5 三消动画

满足条件后播放：

1. 三枚卡片放大至 1.12
2. 停顿 40ms
3. 星光粒子（6~10 个）
4. 缩小至 0 + Fade
5. 剩余 Tile 左移紧凑（120ms）
6. Combo +1

**总时长 320～450 ms，不得超过 600 ms。** 频繁三消时节奏会拖沓。

# 5. 胜负规则

## 5.1 胜利

```text
所有 columns 为空 AND tray 为空
```

流程：最后一次三消 → 0.3s 停顿 → 星星 / 彩纸 → 胜利弹窗。

弹窗内容：第 X 关完成、星级、步数、撤回次数、[下一关]、[再玩一次]。

## 5.2 失败

```text
tray.length === traySize (7)  AND  不存在任何 type 计数 >= 3
```

> 注意：由于 §4.2 是"随时三同即消"，只要 tray 满了就**必然**不存在三同（否则早已消除）。因此实际判定可简化为 `tray.length === traySize`。但代码中保留完整条件，作为不变量断言。

**输入锁定：** tray 满时不允许再点击任何 Tile（§3.3）。这比"允许点击然后立即判负"体验好得多——玩家能看到自己正在走向死路，而不是被突然宣判。

失败界面文案：

```text
这一步卡住啦！
```

按钮：[撤回一步]、[重新开始]、[打乱]（若还有次数）、可选：[看视频继续]

H5 MVP 不接真实广告，程序预留 `RewardedAdProvider`，开发环境用 mock（点击后直接成功）。

## 5.3 「软失败」的处理

存在一种情况：tray 未满，但棋盘剩余牌**理论上已无法通关**（例如 tray 里 6 张各不相同，棋盘只剩 3 张且分属 3 类）。

**MVP 不做主动检测。** 理由：

1. 运行时跑 Solver 成本高，且会拖慢每一步
2. 玩家会自然撞到 tray 满，走 §5.2 流程
3. 主动弹「你已经输了」体验极差

但**打乱按钮必须在这种局面下能救场**（见 §7）。

## 5.4 边界规则定义 ★ V0.2 新增

以下 6 条 V0.1 未定义，实现时必然撞上，现在定死：

| # | 场景 | 规则 |
|---|---|---|
| 1 | 打乱后能否撤回？ | **能**。打乱前也 push snapshot，与点击同等对待 |
| 2 | 消除动画中点击其他牌？ | **输入不锁，操作入队**，动画系统串行播放。见 §32.1 |
| 3 | columns 空但 tray 非空？ | **数据错误**。抛错 + 上报，不得静默卡死。这是不变量断言 |
| 4 | 刷新后撤回栈 | **保存最近 5 步 snapshot**（几 KB），刷新后仍可撤回 |
| 5 | 撤回到关卡起始状态后再点撤回 | 按钮置灰，不响应 |
| 6 | tray 满时点击 Tile | 无响应 + 轻微摇晃 tray 提示「满了」（80ms，±4px） |

# 6. 撤回系统

## 6.1 设计原则

每次合法操作（点击 Tile / 打乱）**之前**，保存一次完整状态：

```ts
interface GameSnapshot {
  columns: TileData[][];
  tray: TileData[];
  moveCount: number;
  combo: number;
  rngState: number;      // seeded RNG 的当前状态，打乱可复现
}
```

**用 snapshot，不写反向补丁逻辑。** 关卡最大 90 张牌，一个 snapshot 不到 2KB，栈深 5~20 完全无压力。反向补丁（"撤销一次消除"）的 bug 率是 snapshot 的数十倍。

## 6.2 撤回动画

- Tray 中的 Tile 倒飞回原列顶部
- MVP 可先用 180ms 状态过渡（无飞行轨迹），M4 阶段再补

## 6.3 撤回次数 ★ V0.2 修正

```ts
undoLimit: -1        // -1 = 无限。MVP 全程使用此值
```

**V0.1 建议「每关免费 3 次」，V0.2 改为无限免费。** 理由：

1. 首版目标是**验证体验**，不是变现
2. 撤回一旦限次，玩家在第 3 关卡住 → 直接关页面，我们连"这一关难度是否合理"的数据都拿不到
3. 撤回使用率本身就是最有价值的关卡难度指标（§42），限次会污染这个数据
4. 收紧永远比放开容易——等留存数据出来再说

埋点必须记录 `undo_count`，为后续调整提供依据。

# 7. 打乱系统 ★ 本版重要修正

## 7.1 目的

给玩家「救场」手段，避免局面完全失去可解组合。**打乱是 MVP 唯一的死局解药，必须真正有效。**

## 7.2 打乱规则

只重新排列**棋盘中尚未消除的 Tile**。保持：列数不变、每列当前高度不变、Tile 总数不变、**tray 不变**。

步骤：

```text
1. 收集 columns 中全部 tile type
2. Fisher-Yates shuffle（使用 seeded RNG）
3. 按原列高度重新填回
4. ★ 校验：Solver.canSolve({ columns: 打乱后, tray: 当前 tray }) === true
5. 不通过则重新 shuffle，最多 50 次
6. 仍失败 → 调用 solver.generateSafeState(当前 tray) 兜底
```

## 7.3 为什么第 4 步必须带 tray ★ 关键

V0.1 的校验是「打乱后顶部是否存在三同类」。**这个校验几乎没有意义：**

- 它没有考虑玩家 tray 里已经占了几格
- 假设 tray = `[PAW, GRASS, CAN, BELL, FISH, YARN]`（6 格已满，只剩 1 格），打乱后即使顶部有 3 个 PAW，玩家也只能再点 1 张，照样死
- 结果：打乱按钮变成安慰剂，玩家点了没用，信任崩塌

正确的校验是**以玩家当前 tray 状态为起点，整局是否仍可解**。这需要 §12 修正后的 Solver 支持（tray 进状态）。

## 7.4 打乱次数

```ts
shuffleLimit: 3      // MVP 每关 3 次，免费
```

比撤回稀缺（撤回无限），因为打乱是"洗掉当前局面"的强力手段，无限打乱会让关卡设计失去意义。

# 8. 提示功能

MVP 隐藏 UI，代码预留（`hint` 在关卡 JSON 中默认 0）。

**提示算法（V0.2 修正）：** 不是简单统计顶部同类数，而是：

```text
1. 优先：tray 中已有 2 张同 type 的，在棋盘顶部找第 3 张 → 高亮
2. 其次：棋盘顶部存在某 type >= 3 → 高亮其中 3 个
3. 兜底：读取关卡 JSON 预存的 solution，给出下一步
```

第 1 条最有价值——它对应玩家最常见的困境「我攒了 2 个，第 3 个在哪」。

动画：`scale 1.0 → 1.08 → 1.0`，循环 2 次。**不自动替玩家点击。**

# 9. 关卡设计

## 9.1 基本原则（硬性约束）

```text
totalTileCount % 3 === 0
count(每种 type) % 3 === 0
```

违反任一条 → `validate-levels` 直接报错，不允许进入构建。

## 9.2 难度维度 ★ V0.2 重新排序

V0.1 把「Tile 总数」当作主要难度来源，**这是错的**。Tile 总数决定的是**单局时长**，不是难度。

真正的难度旋钮，按影响力排序：

### 1️⃣ 图案种类数 vs 槽位数（最强旋钮）

这是本品类难度的**第一来源**，V0.1 完全没建模。

```text
槽位 7 格，图案 3 种  → 绝对安全（数学上不可能满，见下表）
槽位 7 格，图案 4 种  → 极宽松（理论可死，实际极少触发）
槽位 7 格，图案 6 种  → 适中（需要开始取舍）
槽位 7 格，图案 8 种  → 紧张（随手捞就会满）
```

**数学关系：** tray 中每种 type 最多能停留 2 张而不触发消除（第 3 张立即消除）。因此**理论上最多可以塞进 `typeCount * 2` 张牌而不成三**：

| 图案种类 | 最多可暂存不成三 | vs 7 格槽 | 死局可能性 |
|---:|---:|---|---|
| 3 | 6 | 6 < 7 | **数学上不可能死局** |
| 4 | 8 | 8 > 7 | 可能，但需极端凑巧 |
| 5 | 10 | 10 > 7 | 有真实压力 |
| 6 | 12 | 12 > 7 | 明显压力 |
| 7 | 14 | 14 > 7 | 高压 |
| 8 | 16 | 16 > 7 | 极高压 |

**唯一的"绝对安全区"是 3 种图案**（6 < 7，无论怎么点都不可能填满 tray）。这是 §10 中第 1、2 关采用 3 种图案的原因——**新手关的"不会输"是数学保证的，不是靠关卡设计小心翼翼堆出来的。**

从 4 种图案开始，死局在理论上就已存在；但要真的死，玩家需要凑巧让 4 种牌各积 2 张（8 张，超过 7 格），实际概率很低。**真正的压力从 5 种图案开始明显上升**，每多一种，可暂存上限就多 2 张，而槽位始终是 7。

> 📌 **推论：**
> - 第 1~2 关用 3 种图案 → **零风险教学区**
> - 第 3~5 关用 4 种图案 → 理论有风险、实际几乎不会触发的**软着陆区**
> - 第 6 关引入第 5 种 → 第一个**真实**难度台阶
> - 第 10、17 关各加一种 → 后续台阶

### 2️⃣ 同类牌的空间离散度

3 个 PAW 的分布位置：

```text
同层、相邻列        → 极简单（一眼看到，连点三下）
同层、分散列        → 简单
不同层、深度差 <= 2 → 适中
深度差 >= 5         → 难（必须先挖开，占用槽位）
一个在 col0 底部    → 陷阱（几乎必须撤回）
```

量化指标：`avgDepthSpread = 平均(同 type 三张牌的最大深度 - 最小深度)`

### 3️⃣ 列深（最大列高度）

越深，需要提前规划越多。但**列深 > 12 会导致小屏排不下**（见 §19），MVP 上限 10。

### 4️⃣ 陷阱密度

「误选后需要撤回几步才能恢复」。教学关设为 0，中期关卡 1~2，后期 3+。

### 5️⃣ Tile 总数（只控时长，不控难度）

按每步约 1.2~1.5 秒估算：

```text
36 张 → 约 50 秒
54 张 → 约 75 秒
72 张 → 约 100 秒
90 张 → 约 130 秒
```

目标单局 1~3 分钟 → **正常关卡规模 54~90 张**。

# 11. 关卡生成策略

首版**不使用完全随机生成**，必须生成「已知可解」的棋盘。

## 11.1 逆向生成思路

先生成一个必定能消除的解题顺序：

```text
AAA  BBB  CCC  AAA  DDD ...
```

每 3 个一组，然后**倒序**将这些 Tile 分配到各列。因为我们知道正确取牌顺序，理论上一定存在解。

## 11.2 生成步骤

```ts
function generateSolvableLevel(config: LevelConfig, rng: SeededRandom): Column[] {
  const groups = createTripleGroups(config, rng);   // 按 typeCount / tileCount 生成三元组
  const columns = createEmptyColumns(config.columnCount);

  for (const group of reverse(groups)) {
    distributeGroupIntoColumns(group, columns, config, rng);
  }

  // 双重校验
  if (!solver.canSolve({ columns, tray: [] })) return generateSolvableLevel(config, rng);
  if (!difficultyInRange(columns, config)) return generateSolvableLevel(config, rng);

  return columns;
}
```

## 11.3 难度定向控制

`distributeGroupIntoColumns` 需要根据 config 控制**同类牌的深度差**（§9.2 的第 2 号旋钮）：

```ts
interface LevelConfig {
  // ...
  targetDepthSpread: [min: number, max: number];   // 例：教学关 [0,1]，后期 [3,6]
  trapCount: number;                                // 深度差 >= 5 的三元组个数
}
```

# 12. Solver ★ 本版核心修正

关卡编辑与自动生成都必须配 Solver。**这是整个项目最值得投入的模块。**

## 12.1 为什么 V0.1 的 Solver 是错的

V0.1 §12.2 把「一组三连」当作一次搜索动作：

```text
统计所有列顶部 → 某 type 顶部出现 >= 3 → 一次弹三张
```

**这个模型只在 traySize = 3 时成立。** 在 7 格规则下它会同时产生两类错误：

**漏解（假阴性）：** 玩家可以先拿 `PAW, GRASS, CAN` 三张不同的牌（都不成三），把三列的下一层露出来，第 4 步才拿到第二个 PAW。这类「先铺垫再收割」的解法，V0.1 的 Solver **永远搜不到**，会把大量好关卡误判为不可解并丢弃。

**放过死局（假阳性）：** 它完全没建模 tray 占用，因此无法发现"槽位被塞满导致的死局"——而这恰恰是本品类唯一的失败方式。

## 12.2 正确的状态定义

```ts
interface SolverState {
  columns: TileType[][];
  tray: TileType[];        // ★ 必须进状态
}
```

## 12.3 动作定义

```text
动作 = 取某一列的顶部一张（不是取三张）

合法条件：
  - 该列非空
  - tray.length < traySize

apply 后：
  - tray 插入该 type
  - while (存在 type 计数 >= 3) 移除该 3 张   ← 确定性，不产生分支
```

## 12.4 剪枝（决定 Solver 能否用于生产）

没有这些剪枝，54 张牌的关卡会直接搜爆。按重要性排序：

**1️⃣ Canonical Hash：列顺序无关（最重要）**

**列的左右顺序在规则上完全无意义。** 把列内容排序后再 hash，状态数会掉 1~2 个数量级。

```ts
function hashState(s: SolverState): string {
  const cols = s.columns
    .filter(c => c.length > 0)
    .map(c => c.join(','))
    .sort();                        // ★ 列排序
  const tray = [...s.tray].sort();  // ★ tray 也排序（tray 内顺序同样无意义）
  return cols.join('|') + '#' + tray.join(',');
}
```

**2️⃣ 同顶部类型的列去重**

若 col2 和 col5 顶部都是 PAW，只搜其中一个（对称性）。

**3️⃣ 死路剪枝**

```text
tray.length === traySize  → 必死（因为随时三同即消，满了就是无解）→ 立即返回 false
```

**4️⃣ 计数可行性剪枝**

```text
对每个 type：count(columns 中该 type) + count(tray 中该 type) 必须 % 3 === 0
否则该分支必然无法清空 → 剪掉
```

**5️⃣ 节点上限**

```ts
const MAX_NODES = 2_000_000;   // 超出视为不可解（保守），并在 validate 时告警
```

## 12.5 DFS + Memo

```ts
function canSolve(state: SolverState, memo: Map<string, boolean>, budget: Counter): boolean {
  if (isEmpty(state.columns) && state.tray.length === 0) return true;
  if (state.tray.length >= TRAY_SIZE) return false;         // 剪枝 3
  if (budget.exceeded()) throw new SolverBudgetExceeded();  // 剪枝 5

  const hash = hashState(state);
  if (memo.has(hash)) return memo.get(hash)!;
  memo.set(hash, false);                                    // 防环：先标记 false

  for (const colIdx of getDistinctTopColumns(state)) {      // 剪枝 2
    const next = applyPick(state, colIdx);
    if (!countFeasible(next)) continue;                     // 剪枝 4
    if (canSolve(next, memo, budget)) {
      memo.set(hash, true);
      return true;
    }
  }
  return false;
}
```

## 12.6 运行时预算 ★ V0.2 修正

V0.1 说「关卡生成阶段允许 50~200ms」——**这个预算对 DFS 太紧了**。

V0.2 规定：

```text
✅ Solver 只在构建期运行（npm run validate-levels）
   预算：每关 10 秒，可接受

✅ 产物写入关卡 JSON 的 solution 字段

❌ 运行时永远不跑 Solver
   提示功能读取预存 solution（§8 第 3 条兜底）
```

**唯一例外：** 打乱时的可解性校验（§7.2 第 4 步）必须在运行时跑。为此设置严格预算：

```ts
const SHUFFLE_SOLVER_BUDGET_MS = 80;   // 超时视为不可解，重新 shuffle
```

由于打乱发生在局中（棋盘已消掉一部分），剩余状态空间通常远小于初始局面，80ms 足够。

# 13. 可解性保障：三层防线 ★ V0.2 重构

V0.1 只有「Solver 校验可解」一层。**这不够。**

Solver 只能证明「**存在**一条通关路径」。但玩家会走错。走错之后 tray 塞满废牌 → 死局。**这才是本品类真正的运营难点。**

## 第 1 层：构建期 Solver 校验（保证理论可解）

```bash
npm run validate-levels
```

输出：

```text
20/20 levels schema valid
20/20 levels count-divisible (total % 3, per-type % 3)
20/20 levels solvable (solver)
```

## 第 2 层：随机玩家模拟器（保证人类玩得通）★ V0.2 新增

**这个工具比 Solver 有用得多。** Solver 告诉你「理论可解」，模拟器告诉你「人类玩不玩得通」。

```bash
npm run simulate
```

实现：对每关跑 N=1000 次模拟，玩家策略为「贪心 + 随机」：

```ts
function simulateGreedyPlayer(level: Level, rng: SeededRandom): SimResult {
  // 策略优先级：
  // 1. 若 tray 有 2 张同 type，且棋盘顶部有第 3 张 → 取它（收割）
  // 2. 若棋盘顶部有 3 张同 type → 取其中一张（铺垫）
  // 3. 否则 → 在顶部随机取一张（探索）
  // 记录：是否通关、步数、最大槽位占用
}
```

输出分级：

```text
Level  1: deadlock  0.2%  avgMoves  18  maxTray 3/7   ✅ 教学
Level  6: deadlock  8.4%  avgMoves  52  maxTray 6/7   ✅ 良好
Level 13: deadlock 34.1%  avgMoves  71  maxTray 7/7   ⚠️ 偏难
Level 18: deadlock 61.7%  avgMoves  84  maxTray 7/7   ❌ 过难，需重做
```

**判定阈值：**

| 死局率 | 判定 | 动作 |
|---|---|---|
| < 2% | 过于无脑 | 教学关（1~5）可接受，其他关告警 |
| 2% ~ 30% | ✅ 健康 | 通过 |
| 30% ~ 45% | ⚠️ 偏难 | 告警，人工复核 |
| > 45% | ❌ 过难 | **构建失败** |

> 📌 这直接对应 V0.1 §42 的运营指标「失败率 > 45% 应优先检查关卡设计」。区别在于：**V0.2 让这个指标在上线前就能拿到**，而不是等真实玩家流失后才发现。

## 第 3 层：运行时救场（保证玩家不会真的卡死）

1. **撤回无限免费**（§6.3）
2. **打乱带 tray 校验**（§7.3）——保证打乱后真的能继续
3. **tray 满时锁输入**（§3.3）——让玩家看见危险，而不是被突然宣判

# 16. 新手教学

## Level 1 —— 教「只能点顶部」

初始棋盘明确露出 3 个爪子，且**只有爪子可点**（其他列顶部都是被遮挡的视觉暗示）。

手指动画依次提示三下。

```text

```

## Level 2 —— 教「三枚同类自动消除」

```text
集齐 3 个相同图案就会消除
```

在玩家攒到第 2 个同类时，高亮暂存槽并提示：`还差 1 个！`

## Level 3 —— 教「槽位可以暂存不同类」★ V0.2 新增，最关键的一关

这是 V0.2 新增的教学目标。**7 格规则下，玩家必须理解"可以先捞不同类的牌"，否则会一直不敢点。**

设计：初始局面**故意让顶部没有任何三同类**，玩家必须先取 2~3 张不同的牌，才能露出可消的组合。

> 注意：Level 3 是首个使用 4 种图案的关卡（§10），此时死局在理论上首次成为可能。但由于只有 36 张牌且深度差被压到 [0,2]，实际触发概率极低——**这一关要教会玩家"敢暂存"，而不是吓退他**。

```text
凑不齐？先放进下面的格子里，等后面再补
```

失败（tray 满）时提示：

```text
格子满了！点击「撤回」把牌放回去
```

## Level 4~5 —— 放手

不再强制引导，只在玩家 15 秒无操作时给出 hint 动画。

# 19. 棋盘自适应布局 ★ 本版核心修正

## 19.1 V0.1 的约束冲突

V0.1 §19 要求 8 列 + `tileSize min = 54px`。实测：

```text
375px 屏（iPhone SE / mini / 12 mini）
左右各留 16px padding，列间 gap = 4px

tileSize = (375 - 32 - 7*4) / 8 = 39.4px

39.4 < 54  ❌ 约束直接冲突，8 列在小屏上排不下
```

**必须在 M0 阶段解决**，否则 M3 做完 UI 才发现排不下，返工成本极高。

## 19.2 V0.2 决定：MVP 固定 6 列

```text
375px 屏，padding 16*2，gap 6*5

tileSize = (375 - 32 - 30) / 6 = 52.2px
```

52.2px 接近但略低于 54。因此同时把最小值下调：

```ts
const TILE_SIZE_MIN = 48;   // CSS px（V0.1 为 54）
const TILE_SIZE_MAX = 92;
```

48px 的 Tile 在 375px 屏上，图案区域约 32×32px——**足够辨识，前提是图案必须"简形化"**（见 §20）。

**为什么不是 5 列：** 5 列会让棋盘显得过空，且同一时刻可选项只有 5 个，策略空间太小。6 列是可读性与策略性的平衡点。

## 19.3 8 列作为大屏可选（不在 MVP）

```ts
// 后续版本可开启
const columnCount = screenWidth >= 414 ? 8 : 6;
```

**但这需要每关准备两套关卡数据**，MVP 不做。留作 V1.1 讨论。

## 19.4 纵向布局：必须支持重叠 ★ V0.1 遗漏

参考截图中，卡片是**部分重叠**堆叠的（能看到下面卡片的上边缘），不是紧密网格。

**这个重叠是本品类的视觉标志**——它让玩家能看到"下面还有几层"，从而产生规划感。若做成不重叠的紧密网格，玩家无法感知列深，规划体验会大幅下降。

```ts
// 横向
tileSize = clamp(
  (boardWidth - (columnCount - 1) * gap) / columnCount,
  TILE_SIZE_MIN,
  TILE_SIZE_MAX
);

// 纵向 ★ V0.2 新增
const OVERLAP_RATIO = 0.85;              // 建议 0.82 ~ 0.88
rowStep = tileSize * OVERLAP_RATIO;      // 相邻两张的纵向步进
columnHeight = tileSize + (depth - 1) * rowStep;
```

**最大列深校验（M0 必做）：**

```text
375×812 屏：tileSize = (375 - 32 - 30) / 6 = 52.2px
depth = 10, OVERLAP_RATIO = 0.85
columnHeight = 52.2 + 9 * (52.2 * 0.85) = 452px

棋盘区可用高度 ≈ 812 * 0.58 = 471px
452 < 471  ✅ 通过（余量 19px）
```

三种重叠比例的实测对比（tileSize 52.2, depth 10）：

| OVERLAP_RATIO | columnHeight | 余量 | 评价 |
|---:|---:|---:|---|
| 0.80 | 428px | 43px | 安全，但下层露出少、列显得挤 |
| **0.85** | **452px** | **19px** | ✅ 推荐 |
| 0.88 | 466px | 5px | ⚠️ 余量过小，若选此值需把最大列深降到 9 |

因此 §10 难度表中 **最大列深锁定 10，OVERLAP_RATIO 默认 0.85**。

> 最窄屏 360×800 的校验：tileSize = (360-32-30)/6 = 49.7px，
> columnHeight = 49.7 + 9*42.2 = 430px，可用高度 800*0.58 = 464px。✅ 通过。

## 19.5 空间不足时的降级顺序

```text
1. 优先缩小 tileSize（直到 TILE_SIZE_MIN）
2. 再减小 OVERLAP_RATIO（直到 0.78，重叠更多）
3. 再缩小 gap（直到 4px）
4. 仍不够 → 关卡数据超规格，validate-levels 应提前拦截
```

**绝不允许棋盘被暂存槽或工具栏遮挡。**

# 31. 点击逻辑伪代码

```ts
async function onColumnTap(columnIndex: number) {
  // 入队而非直接拒绝（§32.1）
  if (model.status !== 'playing' && model.status !== 'animating') return;
  if (!rules.canPick(model.state, columnIndex)) {
    if (model.state.tray.length >= model.state.traySize) {
      animation.shakeTray();                    // §5.4 规则 6
      haptic.vibrate([20]);
    }
    return;
  }

  undoManager.push(model.snapshot());
  model.status = 'animating';

  const result = rules.pick(model.state, columnIndex);
  await animation.moveTileToTray(result.tile, result.traySlotIndex);
  await animation.shiftTrayTiles(result.shifted);

  const matches = rules.resolveMatches(model.state);   // ★ 可能多次
  for (const m of matches) {
    await animation.playMatch(m.tiles);
    await animation.compactTray(m.remaining);
  }

  if (rules.isWin(model.state))  { model.status = 'won';    return showWin();  }
  if (rules.isFail(model.state)) { model.status = 'failed'; return showFail(); }

  if (model.state.tray.length === model.state.traySize - 1) {
    animation.startTrayWarning();               // §23.6
  }

  model.status = 'playing';
  saveSystem.saveRun();
}
```

# 32. 游戏状态机

```text
BOOT → PRELOAD → HOME → LEVEL_SELECT → PLAYING ⇄ ANIMATING
                                          ↓
                                     WON / FAILED
```

## 32.1 输入处理：入队，而非锁死 ★ V0.2 修正

V0.1 §32 规定「任何动画期间禁止重复输入」。**这会让连续三消手感发滞**——玩家看到三张同类，想连点三下，但第二下被吞掉了。

V0.2 改为**操作入队**：

```ts
class InputQueue {
  private queue: number[] = [];
  private processing = false;
  private static readonly MAX_QUEUE = 2;   // 最多缓存 2 次点击，防止连点炸弹

  enqueue(columnIndex: number) {
    if (this.queue.length >= InputQueue.MAX_QUEUE) return;
    this.queue.push(columnIndex);
    void this.drain();
  }

  private async drain() {
    if (this.processing) return;
    this.processing = true;
    while (this.queue.length > 0) {
      const idx = this.queue.shift()!;
      await onColumnTap(idx);      // 串行执行，规则判定基于最新 state
    }
    this.processing = false;
  }
}
```

**关键点：** 出队时**重新执行规则判定**（`canPick`），因为 state 可能已变（列已空 / tray 已满）。这既保证了状态正确，又保证了手感。

这是达成 §60「Tile 点击延迟低于 100ms」的必要条件。

# 64. 第一版 Demo 验收关卡

手工准备一个 12 张牌的关卡：

```text
Column 0: BELL, PAW
Column 1: GRASS, PAW
Column 2: CAN, PAW
Column 3: BELL, GRASS
Column 4: CAN, GRASS
Column 5: BELL, CAN
```

（数组顺序 bottom → top）

初始顶部：`PAW PAW PAW GRASS GRASS GRASS`

**验收路径 A（简单路径）：**

```text
PAW×3 → 消除 → GRASS×3 → 消除 → CAN×3 → 消除 → BELL×3 → 消除 → WIN
```

**验收路径 B（验证 7 格暂存，V0.2 新增）：**

```text
依次点 col0, col1, col2  → tray = [PAW, PAW, PAW] → 立即消除
依次点 col3, col4, col5  → tray = [GRASS, GRASS, CAN]  ← 不消除，正常暂存
再点 col3 → tray = [GRASS, GRASS, GRASS, CAN] → GRASS 消除 → tray = [CAN]
```

> 路径 B 是 V0.2 规则的关键验收点。**在 V0.1 规则下，路径 B 的第二步就会判负**——这正是两版规则差异最直观的体现。

# 65. 最终建议

这类产品真正决定品质的不是规则复杂度，而是：

1. **顶部信息是否一眼能读懂；**
2. **每次三消是否有明确而舒服的反馈；**
3. **暂存槽的「张力—释放」循环是否成立；** ★ V0.2 新增，这是本品类的灵魂
4. **关卡是否真的可解、而且人类玩得通、难度自然增长；**
5. **误操作之后是否有合理恢复手段；**
6. **移动端是否始终流畅、按钮足够大、没有布局跳动。**

开发优先级：

```text
规则正确
> 可解性保障（Solver + 模拟器 + 打乱救场）
> 点击与消除手感
> 移动端适配
> 美术丰富度
> 商业化
```

首版只要把这条主链做到足够顺滑，就已经是一款完成度很高的 H5 休闲小游戏。

# 附录 A：留给 Codex 讨论的 6 个开放问题

以下是 V0.2 已给出**建议值**但**仍可讨论**的决策点。建议在动工前与 Codex 逐条确认：

| # | 问题 | V0.2 建议 | 讨论要点 |
|---|---|---|---|
| A1 | traySize 到底取 7 还是 6？ | **7** | 7 是行业标准。关键分界在 §9.2 的 `typeCount*2` 公式：**取 7 时，3 种图案是绝对安全区**（6<7），教学关的"不会输"由规则保证；**若改为 6，则 3 种图案变成 6=6 临界**，教学关也可能死局，会失去这个数学保证。若想要更硬核，建议用"关卡可配 traySize"（前 10 关 7 格、后 10 关 6 格）而不是全局降到 6 |
| A2 | MVP 列数 6 还是 8？ | **6** | 6 保证 375px 小屏可用。若产品经理坚持还原截图的 8 列，需接受 tileSize 降到 ~40px，并让美术按 24×24 的辨识标准出图——建议先出一版 8 图标的 24px 缩略图做眯眼测试再定 |
| A3 | 撤回无限 vs 限次 | **MVP 无限** | 无限有利于收集难度数据；若担心玩家"无脑撤回"降低成就感，可改为"无限但记录次数并影响星级"（§15 已是这个设计） |
| A4 | 是否需要主动检测「软失败」？ | **不做** | 见 §5.3。若后续数据显示玩家在死局中反复空转，再考虑加"打乱建议"的柔性提示 |
| A5 | 关卡是手工设计还是全自动生成？ | **1~5 手工，6~20 生成器 + 人工校验** | 教学关的局面必须精确控制（§16），生成器难以保证。中后期关卡靠 `targetDepthSpread` 参数控制 |
| A6 | 纵向重叠比例 0.85 是否合适？ | **0.85，可调** | 实测深度 10 时列高：0.80→428px、0.85→452px、0.88→466px，可用高度约 471px（812×0.58）。**三者都能放下，但 0.88 只剩 5px 余量，风险偏大**。建议 M0 布局验证时同时出三版截图，在"可读性"和"余量"之间人工定夺；若最终选 0.88，需把最大列深降到 9 |
